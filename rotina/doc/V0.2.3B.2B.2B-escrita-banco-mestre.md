# V0.2.3B.2B.2B — escrita real do Banco Mestre

**Status final: CONCLUÍDA — VALIDADA NO NAVEGADOR REAL**, conforme confirmação da usuária. Encerramento documental em 19/10/2026. Nenhuma etapa posterior foi iniciada.

## Escopo e arquitetura

A B.2B.2A foi validada no navegador real pela usuária: lista real, detalhe por URL direta, inexistente, escrita bloqueada e isolamento visual A/B. Esta continuação habilita criação e edição no ActivityForm existente usando saveActivity do repository. Não há cópia local persistida no provider, fallback para mocks, novo schema, migration, db push ou alteração de RLS/Auth.

Nova rota carrega somente listAreas pelo reader SSR existente. Edição carrega getActivity(id) e listAreas, entregando ao formulário o bundle completo e a revision retornada pelo banco. UUID invisível/inexistente conserva o estado amigável da leitura. O formulário de edição é identificado por id/revision para inicializar corretamente um novo snapshot carregado.

A escrita passa por `app/banco-mestre/actions.ts`, uma Server Action protegida pelos mecanismos POST/Origin do Next. Ela cria um cliente SSR por execução, verifica getClaims e usa o repository normal com a sessão dos cookies. Não recebe user_id como autoridade, não lê service_role/secret key/senha de banco e não altera o código de Auth. O banco continua impondo ownership, RLS, FK e constraints sob a RPC SECURITY INVOKER existente.

`write-model.ts` valida o envelope em runtime: modo create/edit, estrutura do bundle, revisão inteira positiva obrigatória na edição e validação completa pelo mapper antes de chamar o repository. Create omite revisão; edit envia exatamente a revisão carregada, sem buscar uma nova para sobrescrever concorrência. A gravação usa uma única save_activity_aggregate por tentativa, com o agregado inteiro. O retorno ao browser contém somente sucesso + activityId/revision ou uma categoria/mensagem segura, sem cause, SQL, claims, cookies, dados de sessão ou dump do agregado.

Após sucesso real, a Server Action invalida lista/detalhe por revalidatePath. Só então o formulário navega para o UUID devolvido pelo banco. Não faz atualização otimista da lista, reset antecipado do formulário nem escrita em localStorage. O provider permanece responsável somente pelas props de leitura; o antigo save local foi removido.

O contrato de chamada também é verificado em teste: criação chama `saveActivity(bundle)` com um argumento; edição chama `saveActivity(bundle, expectedRevision)` com dois argumentos.

## UX e integridade

- Novo item e Editar item estão habilitados; continuam sendo os componentes existentes.
- O formulário usa áreas reais. Sem área ativa não há criação nem seed automático: mostra a necessidade de uma área disponível. Edição pode preservar sua área original inativa, sem permitir associar outra área inativa. Não foi criada uma tela de administração de áreas nesta etapa.
- A validação existente de campos/horários/minutos/metas/tipos continua sendo usada. Validação de transporte e constraints SQL continuam prevalecendo no servidor. O campo status já existente no editor continua disponível na edição; não foi criada ação separada de exclusão ou inativação.
- Durante envio, aparece “Salvando item…” e o fieldset fica desabilitado. Uma trava síncrona impede duplo submit antes mesmo do próximo render. Após sucesso a mesma instância do formulário também não envia novamente.
- Erros mantêm o rascunho e mostram somente mensagem segura. Sessão indisponível oferece login. Não há navegação nem invalidação de cache em Conflict/Validation/Unauthorized.
- Conflict bloqueia novo save com o snapshot antigo, sem retry automático ou tentativa de merge/overwrite. A versão digitada permanece disponível para conferência/cópia. A recarga da versão salva exige confirmação explícita de descarte do rascunho e faz uma nova leitura completa. Não é possível forçar sobrescrita pelo botão Salvar.
- A criação mantém o mesmo UUID durante tentativas da instância do formulário. Se uma resposta se perder após commit, repetir o mesmo UUID conflita em vez de criar outra linha. Em falha de rede, conferir a lista/detalhe antes de tentar novamente. Isso não é uma garantia de idempotência entre recargas/navegadores: não há nova tabela ou token persistido.
- Cancelar apenas navega de volta, sem chamar save. Não há dados reais inseridos/editados pelo agente durante implementação ou testes; preparação SQL usa somente PGlite em memória.

## Testes

Correção após validação real: logout em outra aba fazia o proxy redirecionar o POST da Server Action para login antes de `getClaims`, convertendo a resposta em Unknown no formulário. O proxy agora deixa somente POST com header `Next-Action` não vazio nas rotas `/banco-mestre/nova` e `/banco-mestre/[UUID]/editar` chegar à action sem redirecionar por ausência de sessão. O header não é prova de autenticação: o Next continua validando ID/Origin e a action continua exigindo `getClaims` antes de instanciar o repository. GET sem sessão, POST comum e outras rotas preservam os redirects. Nenhuma alteração de Auth/RLS no Supabase.

O teste de regressão simula formulário aberto autenticado, edição do rascunho, logout compartilhado, GET redirecionado e POST passando pelo proxy até a action real sob stubs. Confirma Unauthorized, nenhuma chamada de gravação/invalidação/navegação, rascunho preservado e “Entrar novamente”. Casos adicionais rejeitam a exceção para GET com header, POST sem header e rotas fora do editor. O cenário após a correção foi validado no navegador real pela usuária.

Cobertura complementar: Validation, Unauthorized e NotFound mantêm o rascunho e exibem mensagens seguras; sessão expirada oferece login. PT409 informa alteração em outra sessão. Edição bem-sucedida preserva a revisão original até a chamada e navega usando o ID retornado pelo repository. Os módulos de escrita não importam mocks nem usam o provider como fonte de gravação.

Na repetição das verificações, a execução paralela de PGlite encontrou falta de memória no ambiente. A repetição com `npm run test:db -- --test-concurrency=1` concluiu os 54 testes com sucesso, sem alteração de schema ou dos casos de teste.

Unitários cobrem validação do envelope e revisão, sessão exigida, ausência de invalidação em erro, retorno seguro, carregamento real das páginas nova/editar, revisão original, áreas inativas, loading e trava de duplo envio, preservação de rascunho em conflito/rede, confirmação de recarga e navegação somente após sucesso. Os testes de leitura foram mantidos e ajustados apenas para links/formulários agora habilitados e provider sem save local.

PGlite aplica as seis migrations existentes e verifica create/edit/read dos cinco tipos através do novo write-model + repository + RPC real em memória; IDs/createdAt/revision; rejeição de revisão antiga; rollback integral do mestre e filhas em erro SQL; criação inválida sem linha parcial; escrita cruzada/anon negada por SQL/RLS; repetição do mesmo UUID sem duplicação. Nenhuma migration foi criada ou editada.

Resultado local final: `npm test` 69/69, `npm run test:db` 54/54, `npm run lint`, `npx tsc --noEmit`, `npm run build` e `git diff --check` passaram. Permanece somente o aviso preexistente de cacheComponents/partialPrefetching. Os testes existentes de Auth, mapper, repository, leitura, RLS e smoke continuam passando. Nenhum segredo foi incluído nos arquivos ou relatórios.

## Validação no navegador real — concluída

Confirmação da usuária usando sessões normais e Supabase remoto:

- Criação real funcionando.
- Edição real funcionando.
- Persistência após refresh.
- UUID preservado na edição.
- Lista atualizada após save.
- Conflito em duas abas com PT409.
- Rascunho preservado no conflito.
- Sobrescrita automática impedida.
- Isolamento de escrita A/B funcionando.
- Sessão expirada retornando Unauthorized com “Entrar novamente”.
- Falha de conexão sem falso sucesso e sem perda do rascunho.

Esses resultados são validações reais relatadas pela usuária, além dos testes automatizados registrados acima. Não há validação obrigatória pendente para fechar a B.2B.2B.

## Melhoria residual — não bloqueante

Após recuperar a sessão, uma instância antiga do formulário pode manter visualmente o erro Unauthorized até reload/F5. Melhorar a atualização desse aviso quando a sessão for recuperada, preservando o rascunho. Registrado também no backlog. Esse comportamento visual não invalida a proteção da escrita nem bloqueia o encerramento. Nenhuma correção funcional foi feita neste fechamento.
