> Atualização documental — 20/10/2026: a V0.2.3 foi concluída e validada no navegador real. O Banco Mestre lê, cria e edita dados reais no Supabase, com persistência após refresh. Referências abaixo a mocks como fonte da UI, ausência de persistência ou integração/validação pendente descrevem somente o estado histórico da entrega indicada, não o produto atual. O fechamento está em [B.2B.2B](V0.2.3B.2B.2B-escrita-banco-mestre.md); a especificação atual é [V0.2.4A — Áreas](V0.2.4A-gestao-areas-especificacao.md).


Revisão: 12/10/2026. A B.1 foi aprovada e seu schema foi preservado. Esta entrega prepara a camada de persistência; **a UI continua usando os mocks**. BancoMestreProvider, ActivityForm, páginas, filtros locais e mock-data não foram alterados.

## Arquitetura e arquivos

```text
cliente Supabase browser/server com Database
  → createBancoMestreRepository(client)
  → consulta básica ou RPC pública
  → DTO validado pelo mapper
  → domínio existente + metadata de revision
```

Em `lib/banco-mestre/data/`:

- `database.types.ts`: contrato SQL provisório das nove tabelas, Row/Insert/Update/Relationships e assinaturas das RPCs públicas.
- `contracts.ts`: DatabaseActivityAggregate, SaveActivityAggregateArgs/Result, PersistedActivityBundle, resumo para listagem e interface do repository.
- `validation.ts`: UUIDs, numeric seguro, datas civis, horários, timestamps, inteiro, weekdays ISO e auxiliares de validação.
- `mapper.ts`: aggregateFromDatabase, aggregateToRpc, activitySummaryFromDatabase, areaFromDatabase e timeWindowFromDatabase.
- `errors.ts`: erros de persistência com mensagem segura e diagnóstico técnico em cause não enumerável.
- `repository.ts`: implementação injetável, sem singleton, hooks React ou chamadas ao banco nas telas.

O ActivityBundle **existente** em editor.ts é reutilizado como único agregado do domínio. Reminder/commitment configs, planejamento e grupos fixos já estão em activity.config; goals/rules/windows continuam relações separadas. Não duplicar esse agregado com outro formato de domínio.

`PersistedActivityBundle = { bundle: ActivityBundle; revision: number }`. O resumo de listagem é `{ activity: ActivitySummary; revision }`; ActivitySummary não contém config. Revision não foi introduzida como conceito visual na Activity.

## Database types provisórios

Não foi executado `supabase gen types`: Docker/Podman não estão disponíveis e nenhum banco remoto foi autorizado/acessado. O arquivo é **manual, derivado das migrations e explicitamente temporário**, não finge geração oficial. Os CHECKs SQL continuam representados como text/string nas Rows; o mapper refina discriminadores em runtime.

As nove tabelas possuem tipos Row completos, nullability e Insert required/defaulted, Update e metadados de FK. Numeric aceita number|string na fronteira, inclusive em Goals. Somente schema public está na API tipada; routine_private não foi exposto. A suíte PostgreSQL compara todas as colunas, tipos, nullability, defaults e nomes/colunas de FKs com o catálogo real após aplicar migrations. Isso reduz deriva, mas não substitui geração oficial nem testes da stack/API.

As factories existentes `lib/supabase/client.ts` e `server.ts` agora recebem o generic Database. Cookies, sessão, env, autenticação herdada e uso visual permanecem iguais; a mudança é de tipagem.

Quando a stack completa estiver disponível, em `rotina` e com migrations aplicadas **localmente**:

```powershell
npx.cmd supabase gen types typescript --local --schema public > lib/banco-mestre/data/database.types.generated.ts
```

O arquivo de comparação não existe nesta entrega. Conferir diferenças, preservar exports Row/Json utilizados pela camada e compatibilidade dos DTOs (numeric string precisa continuar sendo validado), substituir o provisório de forma controlada e executar todas as suítes. Não usar projeto remoto para gerar tipos sem autorização. Essa substituição permanece dívida técnica explícita.

## Leitura e reconstrução dos tipos

`aggregateFromDatabase(unknown)` valida o JSON da RPC e devolve PersistedActivityBundle:

| Activity type | Reconstrução |
|---|---|
| reminder | reminder_config obrigatório → referenceDate/reminderTime; hora NULL é omitida |
| commitment | commitment_config obrigatório → date/startTime/endTime; contexto opcional é incorporado |
| fixedActivity | fixed_schedules ordenados e obrigatórios → config.schedules; contexto opcional incorporado |
| variableActivity | planning_context ou config vazio; goals e windows separados |
| checklistGoal | config vazio e ao menos uma Goal |

Todas as relações verificam activity_id/user_id iguais ao mestre, UUIDs, identidade única dentro de cada array e metadata. Configs/cardinalidades/matriz ativa são validadas novamente, mesmo existindo constraints SQL. Dados incompatíveis geram MapperError com o campo técnico, sem `as Activity` nem any.

- Duration: reconstrói unknown/fixed/minimumIdeal; campos residuais, ausentes, frações, zero/negativo e ideal < mínimo são rejeitados conforme o ramo.
- Weekdays: helper único monday..sunday ↔ ISO 1..7. Entrada SQL deve ser ordenada, única e não vazia. Domínio → SQL canoniza ordem sem descartar duplicatas inválidas.
- RecurrenceRule: todos os sete shapes, incluindo interval calendar/day ou week, month/12 anual, monthly weekday ordinal -1 ↔ last e completion sem âncora. Campos não usados devem ser NULL.
- Goal: unit execution/minute exata para count/duration, unidade livre preservada em quantity; minimum/ideal e validity verificados. Numeric strings são validadas **antes** da conversão, para impedir que overflow/fração de contagem arredonde para um valor aparentemente válido. Quantidades viram number finito dentro do teto seguro, mantendo a precisão aproximada do domínio JavaScript, não aritmética decimal exata. Strings exponenciais, hexadecimal, vazias, NaN/Infinity e formatos inesperados são rejeitados. Duration tem limite integer SQL; count exige inteiro seguro.
- TimeWindow: os três shapes estruturais são reconstruídos por timeWindowFromDatabase, com cobertura, dias opcionais e offset de meia-noite. O agregado e o payload aplicam a matriz B.1: somente variableActivity, preferred, weekdays/timeRange e sem vínculo de regra. Isso não libera fixedStart/allowed/forbidden.
- Datas preservam YYYY-MM-DD, com validação gregoriana sem criação de Date/instantes UTC. Time aceita HH:mm ou HH:mm:00 (fração somente zero) e normaliza para HH:mm. Timestamps de auditoria permanecem strings de instante.
- Contexto: NULL vira ausência; travel só existe se ida/volta estiver presente. Zero é preservado. Arrays são ordenados por sort_position e UUID; o domínio não recebe sort_position.

## Gravação e revision

`aggregateToRpc(bundle, expectedRevision?)` gera p_activity/p_relations/p_expected_revision. Envia snapshot completo, incluindo arrays vazios e configs NULL dos ramos não usados, porque a RPC B.1 substitui as relações. Campos opcionais SQL usam NULL; IDs dos filhos existentes são preservados; sort_position usa o índice do array. Não enviar user_id, activity_id dos filhos, revision como valor novo ou timestamps.

O payload é validado integralmente antes de qualquer chamada. Internamente o mapper usa metadata sintética apenas para reaproveitar a validação estrutural do DTO; essa metadata **não sai no payload** nem substitui auth.uid/ownership no servidor. IDs de Activity, Area e relações precisam ser UUIDs; IDs textuais dos mocks são rejeitados. Não há migração automática dos mocks nem uso deles como IDs de produção.

Criação: ActivityBundle com UUIDs novos e status active; expectedRevision ausente gera NULL. Edição: passar a revision devolvida pelo último get/save. A RPC é responsável por detectar conflito e incrementar revision do agregado, inclusive por filhos; não assumir incremento exatamente +1 nem recalcular no cliente. Não existe retry automático de save: um conflito exige decisão posterior de UX/releitura, sem sobrescrever dados silenciosamente.

## Repository

```ts
const repository = createBancoMestreRepository(client);
await repository.listActivities();
await repository.listAreas();
const persisted = await repository.getActivity(id);
await repository.saveActivity(persisted.bundle, persisted.revision);
```

O exemplo é conceitual: nenhum componente passou a instanciar o repository. Receber o retorno de createClient() browser ou await createClient() server, por request no servidor, usando sessão autenticada normal. A implementação não usa service_role ou credenciais globais.

- listActivities: projeção somente da tabela activities, sem configs/filhos e sem N+1. Retorna resumos com duração, status, importância, areaId e metadata revision. Áreas são obtidas por listAreas e podem ser associadas no consumidor futuro; nenhum join é necessário aqui.
- listAreas: inclui ativas/inativas, ordem sort_position/id.
- Ambas listagens fazem páginas de 500, com ordenação determinística, para não truncar silenciosamente no max_rows=1000 da configuração atual. Não movem filtros para SQL. Paginação por offset não representa snapshot entre requests se houver escrita concorrente; cursores/limites UX ficam para integração posterior.
- getActivity: chama somente public.get_activity_aggregate; ausente ou de outro usuário → NotFound, sem revelar existência.
- saveActivity: chama somente public.save_activity_aggregate, uma vez por save; nenhuma gravação individual de tabela.

Migration adicional: `20261012000100_master_read_rpc.sql`. Wrapper público get_activity_aggregate(p_activity_id uuid), STABLE, SECURITY INVOKER, search_path explícito, checagem auth.uid e EXECUTE só authenticated. Na B.2A original reutilizava read_aggregate privado. O hardening B.2A.1 incorporou a consulta no corpo da RPC para revogar EXECUTE/USAGE privados, preservando leitura consistente e RLS, sem alterar sua assinatura. A estrutura de tabelas/triggers da B.1 permanece e o schema privado não é exposto.

## Erros

PersistenceError tem kind Unauthorized/NotFound/Conflict/Validation/Unknown e mensagem futura de UI em português, sem SQLSTATE, nomes de tabela/constraint ou IDs. cause mantém o erro técnico original e não é enumerável/serializado por JSON automaticamente. Nenhum logging automático é introduzido; diagnóstico pode ser inspecionado explicitamente em desenvolvimento. Uma UI futura deve usar kind/message, nunca cause como texto visível.

40001 e 40P01 → Conflict; permissões/JWT → Unauthorized; classes SQL 22/23 e MapperError → Validation; RPC NULL na leitura → NotFound; rede/falhas não classificadas → Unknown. PGRST116 não é transformado genericamente em NotFound, pois também pode indicar cardinalidade indevida. Erros e falhas de mapper são propagados; não retornar vazio/sucesso falso.

## Hardening B.2A.1 aplicado

A migration `20261012000200_private_permissions_hardening.sql` revoga EXECUTE genérico dos helpers e USAGE/CREATE de routine_private para authenticated/PUBLIC/anon. As RPCs públicas get/save permanecem invoker, com EXECUTE só authenticated. Seus corpos incorporam as operações antes delegadas a helpers para manter RLS sem SECURITY DEFINER. O repository, DTOs, Database types e UI não foram alterados.

Somente valid_days/valid_date/valid_time mantêm EXECUTE técnico para CHECKs vinculados por OID, sem USAGE: chamadas qualificadas diretas estão bloqueadas e nenhum helper sensível está autorizado. Default privileges foram ajustados para owners reais e executor; a revogação global necessária de EXECUTE/PUBLIC afeta defaults desses criadores em outros schemas, mas preserva grants locais de outros schemas e ACLs existentes fora do escopo. Um futuro creator diferente exige revisão própria. Decisão, efeito e nove testes específicos estão documentados em [Banco local B.1 — Hardening](V0.2.3B.1-banco-local.md).

A semântica foi verificada em PostgreSQL embarcado: RPC invoker não herda autorização para chamar helpers; CHECKs exigem EXECUTE, e triggers vinculados continuam funcionando sem EXECUTE direto. Os 26 testes de banco anteriores foram preservados. B.2B continua pendente de aprovação; não houve integração UI/Supabase.

Resultado do hardening B.2A.1: npm test 33/33; test:data 24/24 (os mesmos casos incluídos em npm test); test:db 35/35 (26 anteriores + 9 de permissões). Lint, TypeScript, build e git diff --check passaram. O aviso preexistente cacheComponents/partialPrefetching permanece.
