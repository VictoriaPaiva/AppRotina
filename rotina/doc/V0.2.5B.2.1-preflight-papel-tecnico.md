- Configuração local do projeto: Supabase CLI 2.120.0 e major_version=17. Isso não certifica versão/ACL efetivas do banco vinculado nem identifica current_user da implantação remota.
- Ambiente de teste instalado: PGlite 0.5.8 com PostgreSQL **18.3**, identificado por SHOW server_version. Não é PostgreSQL 17 nem o serviço gerenciado Supabase. Docker/psql não foram encontrados no PATH nesta execução.
- Foram aplicadas as seis migrations anteriores e a candidata sob um **current_user não superuser, NOBYPASSRLS, CREATEROLE**, owner dos objetos de domínio. Auth foi modelado com owner separado, USAGE/EXECUTE delegáveis explícitos e sem EXECUTE PUBLIC em auth.uid(). O administrador local só prepara esse ambiente; os comandos da candidata são executados pelo papel restrito de implantação.
- Também foi testada a falta de grant option em Auth: GRANT pode apenas avisar e não conceder nada. A candidata agora verifica os privilégios efetivos do executor e aborta se faltarem.
- Com metas preexistentes de duas contas e uid de instalação nulo, reproduziu-se outra dependência indevida: FORCE RLS bloqueava o próprio backfill pelo instalador sem BYPASSRLS. A candidata agora usa uma policy INSERT temporária somente para CURRENT_USER instalador em activity_goal_versions, remove-a imediatamente após o baseline e confirma sua ausência nos testes. Não desativa RLS nem cria bypass para uid nulo nas funções runtime.
- Não foi executado SQL no Supabase remoto. Não foi usado db push, nem mesmo dry-run, como substituto de teste de privilégio. Validação documental e simulação local não recebem o rótulo “validado no Supabase real”.

## 2. Falha encontrada na candidata anterior

A candidata criava o executor e executava ALTER FUNCTION OWNER TO sem preparar as permissões de implantação. Sob o instalador não superuser, reproduziu-se 42501: ausência de capacidade SET ROLE; isoladamente, conceder SET mas não CREATE no schema também reproduziu 42501.

O [PostgreSQL 17 exige](https://www.postgresql.org/docs/17/sql-alterfunction.html) ownership da função pelo executor do ALTER, capacidade de SET ROLE ao novo owner e CREATE do novo owner no schema da função. O teste anterior com superuser dispensava essas condições e, por isso, não demonstrava portabilidade.

### Correção mínima aplicada somente à candidata

Na mesma transação de implantação:

```sql
CREATE ROLE routine_progress_executor
 NOLOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT
 NOCREATEROLE NOCREATEDB NOREPLICATION;
GRANT routine_progress_executor TO CURRENT_USER WITH INHERIT TRUE, SET TRUE;
GRANT CREATE ON SCHEMA public, routine_private TO routine_progress_executor;
-- criação/transferência das funções e configuração das ACLs/triggers
REVOKE CREATE ON SCHEMA public, routine_private FROM routine_progress_executor;
REVOKE routine_progress_executor FROM CURRENT_USER;
```

SET permite transferir ownership; INHERIT temporário permite ao instalador continuar administrando ACLs e criar triggers sobre funções já transferidas. Sem INHERIT, o instalador não deve presumir privilégios do novo owner só por poder SET ROLE. Nenhuma dessas memberships é concedida ao browser ou authenticator. Remoção e verificações de cleanup ocorrem antes do COMMIT; erro faz rollback de toda a implantação.

Em PostgreSQL moderno, o criador CREATEROLE recebe automaticamente ADMIN OPTION sobre o papel criado. O teste observou uma membership administrativa remanescente com **ADMIN=true, INHERIT=false, SET=false**, separada do grant temporário revogado. Não afirmar que nenhuma linha de pg_auth_members permanece. Isso mantém administração com o instalador confiável que já tem CREATEROLE, sem herança/SET runtime. Não há membership do executor em postgres ou em qualquer papel privilegiado; a direção é executor→instalador administrativo, não postgres→executor.

NOINHERIT não elimina privilégios PUBLIC nem substitui inspeção de cada membership. CREATE efetivo remanescente por PUBLIC ou SET/INHERIT remanescente do instalador causa aborto da verificação final; não revogar CREATE global de PUBLIC automaticamente para “corrigir” um ambiente divergente.

## 3. Matriz de compatibilidade

| Passo | Condição sem superuser | Evidência / estado |
|---|---|---|
| CREATE ROLE e atributos restritivos | Instalador com CREATEROLE; nome livre. Não solicitar SUPERUSER/BYPASSRLS/REPLICATION | Suportado pela regra PostgreSQL; executado localmente sem superuser. ACL do projeto remoto pendente. |
| ALTER FUNCTION OWNER TO | Instalador dono, SET no executor e executor com CREATE temporário em public/routine_private | Falha anterior reproduzida; correção e cleanup testados. |
| SECURITY DEFINER | Owner executor sem login/superuser/bypass e sem ownership das tabelas | Oito funções definer verificadas; funcionamento local após revogar CREATE/SET. |
| row_security=on | SET de parâmetro da função; role sujeito a RLS | proconfig das oito funções conferido; A e B isolados. Não é antídoto para BYPASSRLS, por isso esse atributo fica proibido. |
| auth.uid() pelo owner técnico | USAGE auth + EXECUTE auth.uid; contexto do request continua presente dentro do definer | Verificado com uid técnico A e sessão B sem acessar A; sessão nula rejeitada. Auth real/PostgREST ainda pendente. |
| USAGE public/routine_private | Owner do schema ou grant option do instalador | Schemas do projeto pertencem ao instalador no teste. Não reabrir routine_private para authenticated. |
| USAGE auth / EXECUTE auth.uid | Direitos efetivos concedidos ao executor; instalador pode delegar ou acesso efetivo já existe | Não presumir grant option por o instalador conseguir executar auth.uid. Script de catálogo identifica; candidata aborta se acesso efetivo não existir. |
| CREATE POLICY TO executor | Instalador owner da tabela, papel executor existe | Testado em tabelas antigas e novas; não requer conceder membership executor ao browser. |
| SELECT FOR UPDATE Activity | SELECT + UPDATE(id) restrito e policies owner | Mantido; sem UPDATE histórico concedido para obter lock. |
| Grants em domínio/assert_activity | Owner/grant option dos objetos do projeto | Testado; proprietários remotos precisam ser conferidos. |
| Backfill com FORCE RLS | Policy temporária de INSERT somente para o instalador confiável, removida na mesma transação | Captura de duas contas com uid nulo testada; sem policy residual e sem bypass runtime. |

O Supabase [documenta criação de papéis](https://supabase.com/docs/guides/database/postgres/roles), mas [não disponibiliza superuser ao postgres do projeto](https://supabase.com/docs/guides/database/postgres/roles-superuser). Não converter essa documentação geral em prova de que o login efetivo de migrations deste projeto possui todos os grants necessários.

## 4. auth.uid, SECURITY DEFINER e limites de confiança

SECURITY DEFINER muda current_user para o owner, mas não autentica uma pessoa por esse nome. O identificador funcional continua vindo de auth.uid() no contexto do request estabelecido pelo PostgREST. auth.uid() não deve ser substituído por current_user/session_user, UUID de input nem JWT recebido manualmente.

O teste local simula a entrada de contexto com UUIDs técnicos fixos; não prova validação criptográfica de JWT. O projeto já valida sessão normal na aplicação; a RPC continua exigindo uid não nulo e RLS. Não expor mecanismo SQL para clientes definirem claims. O script de catálogo não lê request.jwt.claims, não imprime auth.uid e não executa RPC de escrita.

O executor permanece sem acesso de leitura a auth.users: REFERENCES de instalação não é SELECT para runtime. Necessita apenas USAGE auth e EXECUTE auth.uid, além dos grants de domínio descritos na B.2. Seu search_path continua fixo e todos os objetos não pg_catalog são qualificados. [SECURITY DEFINER exige cuidado com search_path e EXECUTE](https://www.postgresql.org/docs/17/sql-createfunction.html).

## 5. Preflight de catálogo preparado para o ambiente real

Arquivo: [progress-role-readonly.sql](../supabase/preflight/progress-role-readonly.sql). Executado e validado somente localmente. Contém BEGIN READ ONLY, SELECTs de catálogos/privilégios e ROLLBACK; nenhum CREATE/GRANT/ALTER ou leitura de dados pessoais.

Procedimento para concluir a evidência remota, sem aplicar candidata:

1. Executar esse arquivo por um canal SQL administrativo já autorizado, **com o current_user efetivo usado nas migrations**. Não solicitar nem colar connection string/senha/JWT no repositório/chat.
2. Conferir current_user e session_user. Se CLI usar papel de login intermediário, confirmar o papel efetivo; resultado do Dashboard não prova que o caminho da CLI é idêntico. A documentação de [migrations Supabase](https://supabase.com/docs/guides/deployment/database-migrations) não substitui essa observação.
3. Exigir CREATEROLE no papel efetivo, ou caminho administrativo documentado que possa assumi-lo; para o objetivo desta etapa, não contar um resultado apenas com rolsuper=true como prova.
4. Conferir owner/CREATE dos schemas e ownership das tabelas/functions do projeto; verificar REFERENCES em auth.users para os FKs novos, USAGE auth e possibilidade de delegação de EXECUTE auth.uid.
5. Ausência do executor antes da candidata é normal. Existência prévia exige auditoria; não usar IF NOT EXISTS para aceitar atributos/memberships desconhecidos.
6. Registrar somente resultados de catálogos/booleans. Qualquer negação ou warning de grant precisa ser resolvido antes da promoção; o arquivo somente de leitura não prova que hooks gerenciados aceitarão CREATE ROLE/ALTER OWNER.

Esse diagnóstico pode comprovar pré-condições do projeto, mas o último teste de DDL com as restrições/versão do serviço deve ocorrer em ambiente Supabase descartável/branch de teste autorizado. Um teste DDL com ROLLBACK ainda é escrita/locks temporários: não foi executado no remoto nem está implicitamente autorizado por chamar-se preflight.

## 6. Alternativas mínimas se o ambiente negar um passo

- **Login intermediário sem CREATEROLE/ownership:** usar o papel administrativo de migrations já previsto pelo projeto, com SET ROLE apenas se a membership existente permitir. Não conceder CREATEROLE ao browser/executor nem tentar assumir supabase_admin. Se o próprio papel administrativo suportado não puder criar o papel restrito, solicitar provisionamento suportado pelo serviço; interromper promoção até haver caminho documentado.
- **ALTER OWNER negado:** a correção padrão é SET/INHERIT e CREATE temporários para implantação, já testada. Uma variante é criar funções dentro de SET ROLE executor e voltar ao instalador para tabelas/policies; ainda exige capacidade SET e CREATE temporário. Não resolve a falta desses privilégios, nem justifica deixar owner postgres nas RPCs como fallback silencioso.
- **Auth não delegável:** primeiro verificar privilégios efetivos, inclusive PUBLIC. Se realmente indisponíveis, alternativa a revisar é um único helper privado sem argumentos, owner instalador confiável, que apenas retorna auth.uid() e não lê/modifica tabelas. Somente o executor recebe EXECUTE; RPCs e policies técnicas chamariam esse helper, mantendo RLS sob executor. Exige revisão/alteração explícita das referências e testes; não está implementado nem confirmado como necessário. Nunca tornar o helper público nem mover toda a RPC para owner com bypass por conveniência.
- **CREATE POLICY negado por owner divergente:** aplicar a DDL como owner autorizado dos objetos existentes ou corrigir o ownership por processo de manutenção aprovado. Não usar policy TO PUBLIC, desativar RLS ou conceder DML histórico ao cliente para contornar a negação.

Nenhuma alternativa usa service_role, senha do executor ou conexão do browser como esse papel. NOLOGIN é preservado.
