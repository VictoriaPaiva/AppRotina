## Endpoint técnico, somente desenvolvimento

`GET /api/dev/data-smoke` verifica a sessão no servidor e usa o cliente autenticado normal com `createBancoMestreRepository`, `listAreas()`, `listActivities()` e `getActivity()`. Aceita `?activityId=<UUID>` para verificar um agregado específico. Sem agregado visível retorna `aggregate: "not-found"`; não retorna dados completos nem claims.

`POST /api/dev/data-smoke` exige sessão e Origin da própria aplicação. Cria um item fictício, salva uma edição, lê o agregado, confirma incremento de revisão, verifica conflito com revisão antiga e inativa o item ao finalizar. Retorna o UUID da fixture. Não exclui registros nem altera itens previamente existentes. Usa somente as RPCs públicas e os grants/RLS normais. As chamadas são transações distintas; falhas de rede podem deixar uma fixture incompleta, e erro na limpeza é reportado. Não executar repetidamente para popular o banco.

Em produção o endpoint retorna 404. Sem configuração, em desenvolvimento, retorna 503; sem sessão configurada, 401. POST sem Origin válido retorna 403. Não há acesso pelo menu do produto nem troca de provider.

## V0.2.3B.2B.1.2 — harness de escrita cruzada e anon

`POST /api/dev/rls-smoke` tem os modos `prepare`, `attack`, `verify` e `anon`. Fora de `NODE_ENV=development` responde 404. GET responde 405 em desenvolvimento e 404 fora dele. Todo POST exige Origin da aplicação via `smokeAccessStatus`, inclusive anon. Falta configuração pública: 503; falta sessão nos modos prepare/attack/verify: 401; entrada inválida ou fixture expirada: 400; check reprovado: 409 com `ok:false` e `failedCheck`; erro interno: resposta genérica sem diagnóstico bruto. Todas as respostas usam `Cache-Control: private, no-store`.

Prepare/attack/verify usam `createClient()` do servidor com os cookies normais do navegador e `getClaims()`. Anon usa uma instância nova de supabase-js somente com URL e publishable/anon key configuradas, sem cookies, storage, refresh, detecção de sessão na URL ou Authorization customizado. Nenhum access_token/JWT é solicitado, transferido manualmente ou guardado. Não há logging de erros, payloads ou credenciais.

Para não retornar `user_id` A, o servidor mantém um registro temporário por UUID de fixture com dono e snapshot técnico. O registro não contém sessão, cookies, claims ou tokens. O navegador recebe somente `activityId`, `revision` e `expectedName`. Não são aceitos dono, nome esperado ou baseline enviados pelo navegador, nem UUID arbitrário fora do registro. Máximo de 32 fixtures registradas, validade de uma hora; reinício/recompilação do servidor perde o registro e exige um novo prepare. Use uma única instância `npm run dev`, sem editar arquivos durante o roteiro. Há exclusão de chamadas concorrentes por fixture; não execute ataques simultâneos. Um ataque concluído não é repetido na mesma fixture.

| Modo | Operações reais, usando os grants/RLS normais |
| --- | --- |
| prepare (A) | SELECT paginado de `user_id` nas nove tabelas, conferido internamente com A sem retornar as linhas. Reutiliza `runRepositorySmoke`: listagens, área técnica se necessária, create/edit/read/stale Conflict/inativação. Lê o snapshot final da fixture própria, variável e sem filhas. |
| attack (B) | SELECT paginado nas nove tabelas para conferir que só há linhas próprias. GET RPC da fixture A deve retornar null. Save RPC com revisão real e snapshot válido tenta trocar o nome técnico. UPDATE direto por ID com RETURNING id tenta outro nome. Dois INSERTs em goals tentam vincular a fixture A, primeiro com dono B, depois com dono A. |
| verify (A) | Confere listagens próprias, existência, nome, revision e snapshot completo pelo repository; consulta goals por activity_id para confirmar ausência de filhas e exige ataque concluído sem falha. Não altera a fixture. |
| anon | SELECT limitado nas nove tabelas: permissão negada (42501) ou nenhuma linha. GET e SAVE RPC devem falhar com 42501; null sem erro não conta como RPC negada. Não usa a sessão do navegador mesmo se a chamada for feita em A/B. |

O payload de goals usa UUID novo, `enabled:true`, `metric:count`, `unit:execution`, `minimum_target:1`, `period:week`, `starts_on:2026-10-19` e `sort_position:0`, além de activity_id/user_id internos. É válido para variável, inclusive inativa; teste SQL confirma inserção própria bem-sucedida. Só 42501/23503 contam como rejeição de filha; 23514/23502/22P02 e erros de rede/formato falham o check. Save cruzado exige PT409 ou 42501; UPDATE exige zero linhas ou 42501. Erros completos nunca são retornados; `codes` contém apenas códigos de uma lista permitida, ou `UNEXPECTED`.

Qualquer check reprovado interrompe a sequência. Uma escrita que devolve sucesso reprova mesmo sem dados retornados; nenhuma limpeza tenta corrigir o resultado. O registro fica bloqueado para novo ataque, mas A ainda pode executar verify. Falha de rede durante uma escrita também bloqueia outro ataque porque o resultado pode ser incerto. **Se houver modificação cruzada, não avance para B.2B.2 e não tente reparar silenciosamente a fixture.** Preserve somente o relatório seguro para investigação. Fixtures ficam inativas no banco; áreas técnicas criadas pelo prepare permanecem. Chamadas são transações separadas, sem rollback global do roteiro.

```js

  method: 'POST', headers: {'Content-Type': 'application/json'},

```

3. No console do perfil B, preencha UUID/revisão com os valores da fixture A e execute:

```js

const attackResponse = await fetch('/api/dev/rls-smoke', {
  method: 'POST', headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({mode: 'attack', ...fixtureA})
});
console.log(attackResponse.status, await attackResponse.json());
```

Espere 200, `ok:true`, todos os `ownRows_*:true` e `crossReadDenied`, `rpcWriteDenied`, `directUpdateDenied`, `childInsertAsBRejected`, `childInsertAsARejected` verdadeiros. Código esperado de save: PT409; filhas: 23503 ou 42501. Se houver `ok:false`/erro, interrompa e execute verify em A para inspecionar a integridade; não repita attack.

4. De volta ao console A, use os mesmos metadados:

```js
const fixtureA = {activityId: prepared.fixture.activityId, expectedRevision: prepared.fixture.revision};
const verifyResponse = await fetch('/api/dev/rls-smoke', {
  method: 'POST', headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({mode: 'verify', ...fixtureA})
});
console.log(verifyResponse.status, await verifyResponse.json());
```

Espere 200 e todos os checks verdadeiros: existência, nome/revisão/snapshot inalterados, nenhuma filha e ataque concluído. Verify anterior ao attack não conclui a validação. Se o console foi reiniciado, monte `fixtureA` com os metadados copiados anteriormente; não crie uma nova baseline para encobrir alterações.

5. Em qualquer perfil, inclusive sem login, execute o modo anon com os mesmos metadados:

```js

  method: 'POST', headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({mode: 'anon', ...fixtureA})
});
console.log(anonResponse.status, await anonResponse.json());
```

Espere 200, `ok:true`, nove `anonSelect_*:true`, `anonGetRpcDenied:true` e `anonSaveRpcDenied:true`, com 42501 para as RPCs. Se qualquer chamada anon for aceita indevidamente, interrompa e faça verify com A; o harness não repara dados.
