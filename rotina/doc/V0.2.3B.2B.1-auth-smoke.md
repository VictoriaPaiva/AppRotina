## Endpoint técnico, somente desenvolvimento

`GET /api/dev/data-smoke` verifica a sessão no servidor e usa o cliente autenticado normal com `createBancoMestreRepository`, `listAreas()`, `listActivities()` e `getActivity()`. Aceita `?activityId=<UUID>` para verificar um agregado específico. Sem agregado visível retorna `aggregate: "not-found"`; não retorna dados completos nem claims.

`POST /api/dev/data-smoke` exige sessão e Origin da própria aplicação. Cria um item fictício, salva uma edição, lê o agregado, confirma incremento de revisão, verifica conflito com revisão antiga e inativa o item ao finalizar. Retorna o UUID da fixture. Não exclui registros nem altera itens previamente existentes. Usa somente as RPCs públicas e os grants/RLS normais. As chamadas são transações distintas; falhas de rede podem deixar uma fixture incompleta, e erro na limpeza é reportado. Não executar repetidamente para popular o banco.

Em produção o endpoint retorna 404. Sem configuração, em desenvolvimento, retorna 503; sem sessão configurada, 401. POST sem Origin válido retorna 403. Não há acesso pelo menu do produto nem troca de provider.

## Complemento do roteiro RLS real — obrigatório antes da B.2B.2

O endpoint de smoke cobre CRUD/revisão/conflict com sessão própria e leitura cruzada. Um HTTP 401 do endpoint NÃO comprova que o PostgREST nega chamadas diretas: ainda faltam os testes abaixo pela API real. Usar apenas fixtures técnicas, nunca dados pessoais, e clientes supabase-js normais separados para A/B/anon, sem chave administrativa. Não registrar session/token/cookies. Executar em projeto de desenvolvimento autorizado, com todas as migrations conferidas.

| Cliente | Operação real adicional | Resultado exigido |
| --- | --- | --- |
| A e B | listAreas/listActivities + consulta direta das duas tabelas | Somente registros próprios |
| B | get_activity_aggregate com UUID da fixture A | Agregado indisponível |
| B | save_activity_aggregate tentando editar fixture A com a revisão de A | Rejeição; leitura posterior na sessão A confirma nome/revisão inalterados |
| B | UPDATE direto da fixture A com RETURNING | Nenhuma linha alterada; A confirma dados preservados |
| B | INSERT de filha vinculada à fixture A usando user_id B; repetir com user_id A | Rejeição por ownership/FK/RLS; nenhuma filha persistida |
| Anon sem sessão | SELECT direto em áreas, atividades e tabelas filhas | Sem acesso aos dados de domínio |
| Anon sem sessão | Chamadas diretas às duas RPCs públicas | EXECUTE negado |

Para o INSERT de filha, usar um payload válido de recurrence_rules ou goals com UUID novo e campos obrigatórios completos, para não confundir erro de formato com isolamento. Em cada teste registrar apenas sucesso/rejeição e SQLSTATE, nunca objetos de erro completos. Se uma operação cruzada for aceita, interromper o smoke e revisar permissões antes de avançar. Nenhuma dessas operações foi executada remotamente nesta entrega; o isolamento SQL local já está coberto nas suítes existentes.
