## Contrato implementado

- `area-contracts.ts`: ManagedArea, AreaSnapshot, CreateAreaInput, RenameAreaInput, SetAreaActiveInput e AreaRepository.
- `area-validation.ts`: validação runtime estrita, chaves extras rejeitadas, UUID validado, nome normalizado com trim, active booleano e snapshot completo. user_id, sort_position e campos de escrita de auditoria não são comandos aceitos. O nome do snapshot não é normalizado: deve comparar o valor original do banco.
- `area-mapper.ts`: reutiliza areaFromDatabase, acrescenta sortPosition e updatedAt. O timestamp original permanece string, sem Date ou arredondamento.
- `area-repository.ts`: factory `createAreaRepository(client, verifiedUserId)` com listManagedAreas/createArea/renameArea/setAreaActive. Nenhum método genérico de save/upsert/delete/ordem.

O chamador servidor futuro precisa verificar a sessão antes de construir a factory e passar o user_id desse contexto, nunca do DTO. A factory não implementa Auth nem torna um UUID confiável por si só. Valida o identificador recebido, restringe consultas por owner e utiliza o cliente Supabase normal, sujeito a RLS. Testes confirmam que um contexto forjado não permite inserir com user_id de outra conta. Não há endpoint/action público novo nesta entrega.

## Persistência e concorrência

Listagem paginada em blocos de 500 com projeção explícita, owner, sort_position/id; inclui áreas inativas. Criação insere somente id técnico estável, user_id fornecido pelo contexto confiável e nome; active/sort_position usam defaults do banco. Colisão de UUID retorna Conflict seguro e não faz upsert.

Renomeação e setActive executam UPDATE condicionado por id, owner e snapshot completo: name, active, sort_position e updated_at. Alteram somente name ou active, respectivamente. O retorno confirmado é mapeado e validado.

Se nenhuma linha mudar, uma consulta mínima de id pela mesma sessão e owner verifica disponibilidade. Linha visível retorna Conflict; ausente/invisível retorna NotFound. Essa consulta ocorre após o UPDATE condicionado e nunca é seguida por retry ou UPDATE incondicional. Erros do banco, rede e mapper seguem PersistenceError e mensagens seguras; não há logging de payloads ou diagnósticos.

Controle de concorrência baseado no timestamp/snapshot do fluxo oficial, sem nova revision de banco. Atualizações PostgREST feitas fora desse fluxo continuam sob os grants/RLS/constraints atuais, como documentado na especificação.

## Validação

Unitários cobrem precisão do timestamp, validação estrita antes de consultas, owner confiável fora do DTO, payload mínimo, colisão, snapshots completos no UPDATE, ausência de retry, NotFound/Conflict, paginação/ordem, retorno inválido e erros seguros. Testes PGlite com as seis migrations existentes cobrem defaults, nomes iguais, concorrência, cada campo do snapshot, A/B/anon, DELETE negado e inativação/reativação com atividade vinculada.

O adapter SQL do teste de áreas recupera timestamps como texto original do PostgreSQL, reproduzindo PostgREST: o decoder padrão de PGlite converte timestamptz em Date e perde microssegundos. Nenhum adapter de produção foi alterado para acomodar testes.

Dados sintéticos existem somente nos testes em memória; nenhum mock/seed participa do repository ou foi inserido remotamente. A UI e o fluxo de atividades permanecem intactos. A próxima parte de B será integração por Server Actions mediante nova instrução, sem iniciar C ou D automaticamente.

Cobertura complementar: todos os comandos rejeitam user_id/userId, timestamps de escrita e sort_position/sortPosition no envelope público. Nome vazio/UUID inválido não chegam ao SQL. Rename em área inativa com sort_position não zero preserva UUID, estado, ordem e created_at. setActive repetido com o mesmo booleano mantém o estado solicitado. UUID recebido é conferido após persistência SQL. NotFound tem mensagem segura uniforme; a API só contém os quatro métodos previstos.

Resultado: `npm test` 78/78; `node --test --test-concurrency=1 tests/db/*.test.mjs` 60/60; `npm run lint`, `npx tsc --noEmit`, `npm run build` e `git diff --check` passaram. Build mantém apenas o aviso preexistente de cacheComponents/partialPrefetching. A tentativa SQL inicial esgotou memória; a repetição sequencial passou. A opção de concorrência precisa vir antes dos caminhos de teste no comando Node, corrigindo o comando anteriormente documentado. Nenhuma validação remota da gestão de Áreas foi realizada nesta entrega.

Não foi encontrada divergência entre o contrato e o schema exercitado no PGlite. A diferença do decoder de timestamp do adapter de teste está descrita acima e não exigiu ajuste funcional. Esta suíte não executa PostgREST remoto; a validação de transporte real continua para a integração/validação posterior e não deve ser inferida dos resultados SQL.
