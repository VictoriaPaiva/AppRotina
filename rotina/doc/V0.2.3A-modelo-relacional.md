## 2. Domínio atual e limites

Item da Rotina é o conceito de produto; `Activity` permanece o nome técnico. O fluxo aprovado é `+ → Item da rotina`, com Projeto e Ideia em breve. Banco Mestre é biblioteca e administração, não uma decisão de destino no fluxo de criação.

| Tipo atual | Configuração própria | Relações aceitas pelo editor atual |
|---|---|---|
| `reminder` | `referenceDate`, `reminderTime?` | Recorrências opcionais |
| `commitment` | `date`, `startTime`, `endTime`, PlanningContext | Recorrências opcionais |
| `fixedActivity` | Grupos FixedSchedule e PlanningContext | Pelo menos um grupo de dias/horários |
| `variableActivity` | PlanningContext, que pode estar vazio | Metas opcionais e janelas preferenciais |
| `checklistGoal` | `config: {}` | Pelo menos uma meta |

`trackingMode` não existe mais. Status é `active`/`inactive`; criação força `active`. Importância é independente. Duration admite somente `unknown`, `fixed` e `minimumIdeal`.

A união TimeWindow declara três effects, duas coverages e três kinds, mas o editor da V0.2.2D aceita apenas preferências de atividade variável, sem vínculo de recorrência e sem fixedStart. O esquema deve preservar a capacidade estrutural da união sem ativar usos ainda não aprovados. A seção 11 distingue estrutura e regras vigentes.

Os dias/horários de FixedSchedule são grupos semanais; não duplicar esses grupos em RecurrenceRule. Recorrência responde quando um item volta a acontecer; Goal responde quanto realizar no período. Anual é um intervalo calendar de 12 meses, não um novo discriminador persistido.

## 3. Alternativas e decisão arquitetônica

| Alternativa | Vantagens | Custos / limitações | Decisão |
|---|---|---|---|
| A. Base comum + cinco configs especializadas | Correspondência literal com a união; FKs e colunas tipadas | Tabelas vazias para checklist; duplicação do contexto; integridade 1:1 exige controle transacional | Boa base, mas reduzir tabelas sem campos próprios |
| B. Base comum + `config jsonb` | Escrita simples e evolução inicial rápida | Validação de cada ramo, referências internas e consultas ficam mais difíceis; tipos gerados não reconstruiriam a união automaticamente | Rejeitada para armazenamento do domínio |
| C. Base comum + configs relacionais necessárias + contexto compartilhado + relações 1:N | Mantém integridade, consultas claras e evita configs artificiais | Leitura com joins; escrita do agregado deve ser transacional | **Recomendada** |

Recomendação: **nove tabelas relacionais**. Não usar JSONB persistido nesta primeira versão. JSON como argumento/resultado de uma futura RPC pode transportar o agregado, sem se tornar uma coluna opaca.

Não criar `fixed_activity_configs`, `variable_activity_configs` ou `checklist_goal_configs` vazias: seus dados já estão em fixed_schedules, planning_contexts e goals. `activities.type` determina o ramo, inclusive quando o contexto da atividade variável está vazio.

Compromisso continua dentro de Activity: compartilha identidade, ownership, busca, edição, área e relações. Sua data/horário fica em commitment_configs; não criar uma segunda entidade mestre apenas por aparecer futuramente no Calendário.

## 4. Convenções e tipos de armazenamento

- Schema proposto: `public`, com RLS em todas as nove tabelas expostas.
- Colunas em snake_case; os valores dos discriminadores conservam os literais atuais, inclusive `fixedActivity`, `minimumIdeal`, `monthWeekday` e `startOnly`. Sem renomear silenciosamente valores na camada de transporte.
- UUID para identidades. PKs independentes recebem `gen_random_uuid()`; configs 1:1 usam o UUID da Activity como PK. Os IDs textuais dos mocks não serão convertidos em IDs de produção. Uma seed de desenvolvimento futura gerará UUIDs e um mapa explícito de relações, sem copiar dados pessoais.
- `user_id uuid NOT NULL` em todas as tabelas, inclusive filhas, referenciando `auth.users(id)` com `ON DELETE CASCADE` para remoção administrativa explícita da conta.
- Timestamps `created_at`/`updated_at`: `timestamptz NOT NULL`, gerados pelo banco, default `now()`; trigger atualiza `updated_at`. Não confiar no relógio do browser para auditoria.
- Minutos de duração/preparação/deslocamento: **integer**, limite 2147483647. Duration exige > 0; preparação/deslocamento permitem zero. Targets duration são numeric com CHECK de integralidade e o mesmo limite; count também exige inteiro. Somente quantity aceita decimais, até 9007199254740991. Nenhum arredondamento de entrada é permitido.
- Intervalos, posição e contadores técnicos: integer com limites explícitos. Os limites de integer são restrições técnicas de persistência; valores maiores devem ser rejeitados, não truncados.
- `sort_position integer NOT NULL DEFAULT 0`, não negativo, nas listas 1:N e áreas: permite reconstruir a ordem das arrays. Não é requisito de UI nova. Ordenação determinística por posição e ID; não exigir posições únicas nesta versão.

A escolha de numeric para targets conserva frações de quantity; ela não elimina a representação aproximada do tipo `number` na aplicação. Os mappers precisarão validar conversões e limites. Referência: [tipos numéricos PostgreSQL](https://www.postgresql.org/docs/current/datatype-numeric.html). Para UUID: [funções UUID](https://www.postgresql.org/docs/current/functions-uuid.html).

## 5. Catálogo de tabelas e colunas

Legenda: NN = NOT NULL; N = nullable. Todas as tabelas recebem os dois timestamps definidos acima. Tabelas filhas recebem `user_id NN` e a FK composta de Activity descrita na seção 6.

### 5.1 areas

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| id | uuid NN, PK | Default UUID |
| user_id | uuid NN | Dono da área |
| name | text NN | `btrim(name)` não vazio |
| active | boolean NN | Default true |
| sort_position | integer NN | Default 0, >= 0 |

UNIQUE `(user_id, id)` para FK composta. Não exigir nome único: a UX não definiu normalização/unicidade de áreas. Eventual deduplicação é evolução separada.

Desativar uma área não desativa nem exclui seus itens. Itens existentes continuam legíveis/editáveis; a edição pode manter sua área desativada atual. Criar item ou trocar sua área requer área ativa. Reativação restaura sua disponibilidade. DELETE de áreas não será permitido ao cliente; não usar SET NULL, pois areaId é obrigatório no domínio.

### 5.2 activities

| name | text NN | Nome não vazio após trim |

| area_id | uuid NN | Área do mesmo usuário |

Todos os valores de duração presentes devem respeitar o teto integer de 2147483647. Usar testes explícitos `IS NULL`/`IS NOT NULL` em cada ramo; comparações sozinhas não proíbem NULL.

### 5.3 reminder_configs

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| activity_id | uuid NN, PK | Uma config por Activity reminder |
| user_id | uuid NN | Mesmo dono da Activity |
| reference_date | date NN | Data civil relevante |

Não representa reserva de agenda. reminder_time não é start_time e não estabelece duração. Referência e anchor_date da recorrência são campos distintos no código atual; não impor igualdade silenciosamente. A primeira data sugerida pelo formulário pode ser a mesma, mas o usuário consegue editar a referência da regra.

### 5.4 commitment_configs

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| activity_id | uuid NN, PK | Uma config por Activity commitment |
| user_id | uuid NN | Mesmo dono |
| date | date NN | Data civil do compromisso |
| start_time | time(0) without time zone NN | Precisão de minuto |
| end_time | time(0) without time zone NN | Maior que início, mesmo dia |

Repetição é opcional em recurrence_rules, inclusive weekdays para terapia recorrente. Nenhuma ocorrência é criada. Duração estimada comum não substitui nem precisa ser igual à diferença desses horários: esta versão mantém os campos independentes como o editor atual.

### 5.5 planning_contexts

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| activity_id | uuid NN, PK | Contexto compartilhado 0:1 |
| user_id | uuid NN | Mesmo dono |
| location | text N | Texto livre não vazio quando presente |
| preparation_minutes | integer N | Finito, >= 0 |
| outbound_minutes | integer N | Finito, >= 0 |
| return_minutes | integer N | Finito, >= 0 |

Só commitment, fixedActivity e variableActivity podem ter contexto. Ausência da linha significa todos os campos ausentes; ao gravar dados totalmente vazios, não criar linha. Zero explícito é preservado e não é ausência. Valores respeitam o teto comum.

Local não vira Location nem entidade de mapas. Ida/volta são durações estimadas, sem rota. No mapper, os dois campos de transporte reconstroem `config.travel` somente se pelo menos um estiver presente. Os tempos associados ao mestre poderão orientar o planejamento futuro, sem bloquear agenda agora.

### 5.6 fixed_schedules

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| id | uuid NN, PK | UUID do grupo |
| user_id | uuid NN | Mesmo dono |
| activity_id | uuid NN | Activity fixedActivity |
| weekdays | smallint[] NN | Conjunto não vazio de dias ISO 1..7 |
| start_time | time(0) without time zone NN | Precisão de minuto |
| end_time | time(0) without time zone NN | Maior que início, mesmo dia |
| sort_position | integer NN | Ordem do grupo |

UNIQUE `(user_id, activity_id, id)`, útil para futura FK de origem da ocorrência. Activity fixa exige pelo menos um grupo na conclusão da transação. Grupos de trabalho seg/ter e qua/qui/sex permanecem duas linhas, não cinco.

Recomenda-se array PostgreSQL: o conjunto é pequeno, fechado e não possui atributos próprios. Uma tabela associativa adicionaria tabelas e operações sem necessidade atual. Usar tabela associativa futuramente somente se cada vínculo dia/grupo tiver configuração própria. Validar array unidimensional, limite inferior 1, cardinalidade 1..7, sem NULLs, duplicados ou valores fora de 1..7; armazenamento ordenado. O tamanho declarado do array não basta para validar esse domínio. Referência: [arrays PostgreSQL](https://www.postgresql.org/docs/current/arrays.html).

Não proibir múltiplos grupos no mesmo dia nem calcular colisões: isso não é uma regra do editor aprovado e depende do planejamento futuro.

### 5.7 goals

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| id | uuid NN, PK | UUID da meta |
| user_id / activity_id | uuid NN | Dono e Activity |
| enabled | boolean NN | Default true |
| metric | text NN | count / duration / quantity |
| unit | text NN | execution / minute / unidade personalizada |
| minimum_target | numeric NN | Finito, > 0 |
| ideal_target | numeric N | Finito, >= mínimo se presente |
| period | text NN | day / week / month |
| starts_on | date NN | Início da validade |
| ends_on | date N | >= starts_on se presente |
| sort_position | integer NN | Ordem da meta |

UNIQUE `(user_id, activity_id, id)`. Metas pertencem a variableActivity ou checklistGoal. Checklist exige pelo menos uma meta cadastrada, mesmo se desabilitada: o editor atual verifica existência, não enabled. Uma atividade pode ter várias métricas ou metas em períodos diferentes; não criar UNIQUE que limite uma meta por Activity/metric.

CHECKs por discriminador:

- count: unit = execution; mínimo/ideal presentes são inteiros positivos.
- duration: unit = minute; valores em minutos totais inteiros, até 2147483647.
- quantity: unit não vazia após trim; preservar unidade escolhida, sem conversão automática.
- Cada valor respeita o teto comum; period e metric pertencem aos conjuntos definidos.

Não persistir progresso nesta tabela, nem traduzir `3x/semana` em weekdays. A transformação `ml → L` encontrada em presentation.ts é somente apresentação; não alterar a unidade armazenada no mapper.

### 5.9 time_windows

| Coluna | Tipo / nulabilidade | Regra |
|---|---|---|
| id | uuid NN, PK | UUID da janela |
| user_id / activity_id | uuid NN | Dono e Activity |
| recurrence_rule_id | uuid N | Vínculo estrutural opcional, mesmo dono e Activity |
| effect | text NN | preferred / allowed / forbidden |
| coverage | text NN | startOnly / wholeActivity |
| kind | text NN | weekdays / timeRange / fixedStart |
| weekdays | smallint[] N | Obrigatório no kind weekdays; opcional nos demais |
| start_time / end_time | time(0) without time zone N | Conforme kind |
| end_day_offset | smallint N | 0 ou 1 somente no timeRange |
| starts_on / ends_on | date NN / N | Validade, fim >= início |
| sort_position | integer NN | Ordem da preferência |

Shape obrigatório:

| kind | weekdays | start_time | end_time | offset / coverage |
|---|---|---|---|---|
| weekdays | Conjunto não vazio | NULL | NULL | Offset NULL; qualquer coverage válida |
| timeRange | NULL = todos; se presente, conjunto não vazio | NN | NN | Offset NN, 0/1; qualquer coverage válida |
| fixedStart | NULL = todos; se presente, conjunto não vazio | NN | NULL | Offset NULL; coverage startOnly |

Para timeRange: offset 0 exige end > start; offset 1 exige end <= start. Isso reproduz a janela positiva de até 24h do editor; start=end com offset 1 significa 24h. Arrays vazios opcionais são normalizados para NULL.

A capacidade SQL de guardar effects e vínculo de regra não autoriza sua criação pela UX atual. Aplicar a matriz vigente da seção 11; uma migration futura poderá ampliar essa regra sem redesenhar a FK.

## 6. PKs, FKs, ownership e exclusão referencial

Todas as linhas pessoais têm user_id próprio. A duplicação nas filhas facilita RLS e filtros; FKs compostas impedem que essa informação diverja do pai. Somente FK de UUID não basta para impedir referência a dados de outro usuário.

| Origem | Destino | Ação referencial |
|---|---|---|
| user_id de todas as tabelas | auth.users.id | DELETE CASCADE somente no fluxo administrativo de conta |
| activities (user_id, area_id) | areas (user_id, id) | DELETE RESTRICT; sem cascata de área para itens |
| Filhas (user_id, activity_id) | activities (user_id, id) | DELETE CASCADE para remoção administrativa do mestre |
| time_windows (user_id, activity_id, recurrence_rule_id) | recurrence_rules (user_id, activity_id, id) | DELETE RESTRICT |

A FK opcional da janela usa o comportamento MATCH SIMPLE: NULL somente em recurrence_rule_id significa sem vínculo. Não utilizar SET NULL indiscriminado na FK composta, pois atingiria user_id/activity_id obrigatórios; remover ou desvincular a janela explicitamente na mesma transação antes da regra.

Nenhum cliente pode mudar user_id, IDs ou created_at após criação. Triggers de integridade protegem essa imutabilidade; RLS também impede transferência a outro usuário. Uma edição de Activity preserva sua identidade. Remover relação e criar outra não pode reutilizar ID pertencente a Activity distinta.

## 7. Enums, text/CHECK e JSONB

Recomendação consistente: **text + CHECK nomeado** para os conjuntos fechados desta versão. Exige migração explícita para ampliar os valores e facilita mudanças durante a evolução do domínio. PostgreSQL ENUM oferece tipagem forte, mas troca/remoção de valores torna a evolução menos simples. Lookup tables só se justificam para cadastros administráveis; Area já é um deles.

Conjuntos: RoutineItemType, ActivityImportance, ActivityStatus, DurationMode, GoalMetric, GoalPeriod, basis, pattern, unit da recorrência, InvalidDatePolicy, effect e coverage. Weekdays/ordinal usam smallint validado. Unidades quantity são texto personalizável, não enum.

Tipos gerados podem representar text como string; a camada de mapper valida/refina para a união TypeScript. Não usar assertions como substituto da validação.

JSONB persistido: nenhum na primeira migration. Um payload de RPC com arrays não altera essa decisão. Snapshots futuros de Occurrence podem eventualmente justificar JSON versionado de dados de exibição; é decisão posterior, sem substituir colunas de identidade, horário e relacionamento.

## 8. Datas civis, instantes e timezone

| Informação | Tipo SQL | Mapeamento |
|---|---|---|
| referenceDate, date, startsOn, endsOn, anchorDate | date | String YYYY-MM-DD, sem conversão UTC |
| reminderTime, startTime, endTime | time(0) without time zone | HH:mm; mapper normaliza HH:mm:ss com segundos zero |
| createdAt, updatedAt; futuros instantes de execução | timestamptz | Instante ISO com offset/Z |

Datas devem ser finitas e no intervalo civil 0001-01-01 a 9999-12-31, coerente com o formato atual. Horários precisam ser >= 00:00 e < 24:00, sem segundos; time(0) por si só não limita ao formato HH:mm. Não usar timetz. Campos locais não devem receber strings com offset.

Um instante timestamptz não conserva o nome IANA do fuso original; guardar um timezone separado quando houver necessidade futura de reproduzir o contexto. Referência: [datas e horários PostgreSQL](https://www.postgresql.org/docs/current/datatype-datetime.html).

Activity continua sem timezone próprio. A futura UserPreferences definirá fuso IANA e início da semana; essas preferências serão necessárias antes de calcular períodos/ocorrências. O formulário usa hoje America/Sao_Paulo como convenção atual, sem implementação de UserPreferences. Não introduzir essa tabela prematuramente apenas para persistir datas civis.

Na futura geração de instantes: combinar data e horário civil com o fuso das preferências, tratar transições de horário de verão e registrar o fuso resolvido na ocorrência/log. Alterar preferências não deve reclassificar silenciosamente datas já registradas de progresso.

## 9. RLS, grants e autenticação

RLS deve acompanhar a criação das tabelas na V0.2.3B, antes de qualquer exposição de dados. Políticas para papel authenticated:

| Tabela | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| areas | Dono | Dono | Dono antigo e novo | Sem política permissiva; cliente não exclui |
| activities | Dono | Dono | Dono antigo e novo | Sem política permissiva; usar status |
| reminder_configs | Dono | Dono | Dono antigo e novo | Dono, sujeito à integridade do agregado |
| commitment_configs | Dono | Dono | Dono antigo e novo | Dono, sujeito à integridade do agregado |
| planning_contexts | Dono | Dono | Dono antigo e novo | Dono |
| fixed_schedules | Dono | Dono | Dono antigo e novo | Dono, sem deixar fixa sem grupo |
| goals | Dono | Dono | Dono antigo e novo | Dono, sem deixar checklist sem meta |
| recurrence_rules | Dono | Dono | Dono antigo e novo | Dono, respeitando janelas vinculadas |
| time_windows | Dono | Dono | Dono antigo e novo | Dono |

“Dono” significa `(select auth.uid()) = user_id`. SELECT/DELETE usam USING; INSERT usa WITH CHECK; UPDATE aplica USING à linha existente e WITH CHECK ao resultado. Conceder apenas os privilégios necessários: não conceder DELETE em activities/areas a authenticated, nem qualquer acesso de domínio a anon. Defaults de user_id, se usados, vêm de auth.uid(); as políticas e FKs continuam obrigatórias.

RLS filtra linhas; não substitui FKs, constraints, grants ou validação de tipo. Usuário anônimo não deve ler dados pessoais. Service role não participa da interface e pode contornar RLS; testes de isolamento não podem usá-la como identidade do usuário. Referência: [RLS do Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

Exigir testes com dois usuários autenticados: leituras, criação, atualização, referências cruzadas de área/Activity/recorrência e tentativa de mudar ownership. Account purge fica em fluxo administrativo futuro, não em DELETE disponível na UX.

## 10. Escrita atômica e concorrência

`saveBundle` hoje substitui a Activity e suas relações numa atualização de estado. O banco deve manter essa atomicidade: vários requests independentes não são equivalentes a uma transação.

Na V0.2.3B, especificar uma função transacional de gravação do agregado, a ser usada pela integração posterior. Preferir SECURITY INVOKER, RLS preservada, referências qualificadas, search_path explícito e execução apenas para authenticated, não PUBLIC/anon. Não implementar SECURITY DEFINER como atalho para ignorar ownership. Referência: [funções no Supabase](https://supabase.com/docs/guides/database/functions).

Contrato sugerido, sem implementação nesta etapa:

1. Resolver auth.uid() e rejeitar sessão ausente; user_id não vem de parâmetro confiável do browser.
2. Na edição, bloquear a Activity do dono; comparar expected_revision para detectar formulário desatualizado. Falha de concorrência deve pedir recarga/revisão, sem sobrescrever silenciosamente.
3. Validar tipo, campos, IDs das relações e área ativa na criação/troca; manter área inativa original é permitido. A área também deve ser bloqueada de modo compatível com desativação concorrente.
4. Preservar ID e created_at; escrever base e config correspondente, remover config/relacionamentos incompatíveis somente após confirmação já tratada pela UX.
5. Upsert por IDs estáveis dos filhos; remover apenas IDs ausentes do agregado enviado. Não deletar/recriar todos os filhos a cada edição: futura referência de histórico precisa de identidade estável.
6. Validar conjunto completo no fim da transação e devolver o agregado final/revision. Qualquer erro desfaz toda a gravação. A aplicação usa a revisão retornada, sem presumir incremento de exatamente 1 por agregado.

revision é mantida pelo banco: começa em 1 e aumenta em cada alteração do mestre; alterações de filhas também atualizam a revisão/timestamp do pai bloqueado. Um agregado com vários filhos pode avançar várias revisões, sempre dentro da mesma transação. Valores de revision enviados pelo cliente não substituem o contador; expected_revision é somente a condição de edição. Assim, uma mudança direta de filha também invalida formulários antigos. Atingir o limite integer deve gerar erro explícito, nunca reiniciar o contador.

Erros previstos: ownership/identidade, área inativa nova, shape inválido, agregado incompleto e edição concorrente. A confirmação da UI não é controle de segurança. A aplicação deve traduzir erros do banco em mensagens, sem mostrar nomes internos ou IDs.

## 11. Constraints locais e integridade entre tabelas

CHECK pode validar a própria linha, mas não é a solução para contar filhos ou consultar o tipo do pai. Também aceita resultado NULL: cada shape precisa testar presença explicitamente. Usar FKs/UNIQUE para referências e triggers para as regras transversais. Referência: [constraints PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).

### 11.1 CHECKs por linha

Implementar na primeira migration real:

- Nomes e textos opcionais presentes não vazios após trim.
- Discriminadores pertencentes aos conjuntos fechados.
- Shapes de Duration, RecurrenceRule e TimeWindow exatamente como nas tabelas acima, proibindo colunas residuais.
- Numeric finito nos limites definidos; positivo para duração/targets; zero permitido em preparo/transporte; ideal >= mínimo; count inteiro.
- Intervalo inteiro positivo; dia 1..31; ordinal 1..5/-1; weekday 1..7.
- Validade sem fim anterior ao início; data civil finita no intervalo definido.
- Horários de minuto, < 24:00; compromisso/grupo com fim > início no mesmo dia; janela com offset 0/1 e intervalo positivo <= 24h.
- Arrays de dias válidos, únicos e não vazios quando exigidos. A helper imutável de validação de arrays deve depender só do argumento, não ler outras tabelas; mudança da helper exige revalidar constraints.
- revision >= 1 e sort_position >= 0.

### 11.2 Matriz vigente de integridade no COMMIT

| type | Config própria obrigatória | Contexto | Grupos | Goals | RecurrenceRule | TimeWindow |
|---|---|---|---|---|---|---|
| reminder | Exatamente 1 reminder_config | Não | Não | Não | 0:N | Não |
| commitment | Exatamente 1 commitment_config | 0:1 | Não | Não | 0:N | Não |
| fixedActivity | Nenhuma config própria | 0:1 | 1:N | Não | Não | Não |
| variableActivity | Nenhuma config própria | 0:1 | Não | 0:N | Não | 0:N preferred, weekdays/timeRange, sem rule_id |
| checklistGoal | Nenhuma config própria | Não | Não | 1:N | Não | Não |

Não permitir reminder_config e commitment_config simultâneas, config sem pai, config do tipo errado ou relações invisíveis incompatíveis. Metas/janelas da variável não definem schedule. A capacidade futura de allowed/forbidden/fixedStart e vínculo de regra permanece documentada na tabela, mas requer ampliar esta matriz numa migration futura.

### 11.3 Mecanismo recomendado

Planejar constraint triggers DEFERRABLE INITIALLY DEFERRED, executadas ao fim da transação, nos pais e nas filhas. Mudança de tipo, inserção/remoção de config, meta, grupo, regra e janela precisam disparar verificação; UPDATE que mover um filho deve verificar ambos os pais. As verificações consultam o estado final, não assumem que o OLD/NEW de um evento intermediário descreve o agregado final. Isso permite salvar base+config e trocar tipo dentro da mesma transação sem estados incompletos persistidos. Referência: [constraint triggers](https://www.postgresql.org/docs/current/sql-createtrigger.html).

Toda mutação de filha deve primeiro serializar no registro da Activity (bloqueio do pai); só deferred trigger sem bloqueio permite corridas ao remover dois últimos filhos em transações simultâneas. O RPC também bloqueia o pai. Quando o pai foi removido em purge administrativo, não exigir sua config/cardinalidade após a cascata. Definir ordem de locks consistente e tratar deadlock/retry no futuro contrato.

Área ativa é verificada na criação ou troca de area_id, não em cada edição nem por trigger que obrigue os itens a desativarem quando a área é desativada. Triggers e FKs mantêm integridade mesmo em requests diretos que não passem pelo formulário.

## 12. Índices iniciais

PK/UNIQUE já geram índices; não duplicá-los. As constraints compostas especificadas acima são necessárias para FKs, mesmo com UUID globalmente único.

| Tabela / índice adicional | Finalidade |
|---|---|
| areas (user_id, sort_position, id) | Lista por dono e ordem |
| activities (user_id, updated_at DESC, id) | Lista principal/paginação do usuário |
| activities (user_id, area_id) | Filtro/FK de área sem varredura global |
| activities (user_id, type, status) | Filtro por tipo e combinação com status |
| Configs 1:1 (user_id, activity_id) UNIQUE | Ownership/FK; não adicionar índice redundante em activity_id, que é PK |
| fixed_schedules/goals/recurrence_rules (user_id, activity_id, id) UNIQUE | Busca das filhas e FKs futuras; já cobre prefixo user/activity |
| time_windows (user_id, activity_id) | Busca de janelas do item |
| time_windows (user_id, activity_id, recurrence_rule_id), parcial quando rule_id presente | Referência futura e custo de exclusão de regra |

Não iniciar índices isolados para cada boolean, importance, cada data ou GIN de weekdays. Lembretes/compromissos ainda não serão consultados por um calendário funcional. Índices por reference_date/date/starts_on e índices de busca textual devem ser acrescentados com a consulta real e seu plano.

A busca atual ignora acentos. Um LIKE simples no PostgreSQL não replica essa experiência; a integração posterior deverá escolher busca normalizada no servidor ou manter filtro local enquanto o volume permitir. Não ligar extensão unaccent/pg_trgm automaticamente nesta etapa.

## 13. Status, remoção e histórico

Para V1, active/inactive é suficiente para o ciclo de vida do mestre. Recomenda-se **não permitir hard delete de Activity/Area ao cliente**, mesmo antes de histórico, para evitar dois comportamentos e preparar preservação futura. Não adicionar deleted_at/archived_at sem uma diferença de produto aprovada.

Filhas podem ser removidas para editar o cadastro sem histórico, respeitando invariantes e FKs. Ao introduzir logs/ocorrências, substituir remoção destrutiva de relações referenciadas por encerramento de validade/versionamento ou bloquear a edição até a política de histórico estar definida. Não fazer cascata que destrua progresso ao trocar tipo.

Desativar Activity interromperá sugestões/geração futura; não apaga execuções passadas. Desativar Goal/Rule também não deveria apagar registros futuros já existentes. A possibilidade atual de trocar tipo mantendo ID é preservada; interpretação histórica exige snapshot/versionamento antes da etapa de histórico, não nesta migration inicial.

## 14. Checklist diário e ProgressLog futuro

Entidade recomendada: `activity_progress_logs`, **adiada**, sem tabela na V0.2.3B inicial.

Os quadradinhos são apresentação de registros dentro de um período, não subtarefas permanentes nem três linhas de cadastro para uma meta ideal 3. Nenhuma linha mestre é resetada à meia-noite.

Campos conceituais para orientar a etapa futura:

| Campo | Papel futuro |
|---|---|
| id / user_id / activity_id | Identidade e ownership, com FK composta ao mestre |
| goal_id? | Contexto opcional de lançamento, FK (user, activity, goal); não limita automaticamente outras metas compatíveis |
| occurrence_id? | FK futura à ocorrência do mesmo usuário e Activity |
| performed_on | Data civil do registro, obrigatória, inclusive entrada retroativa sem hora exata |
| occurred_at? | Instante quando o horário real é conhecido; não inventar meia-noite UTC |
| timezone_at_recording | Contexto do cálculo da data/período; obtido da futura UserPreferences |
| metric / value / unit | Medição: count/1/execution; quantity/valor/unidade; duration/minutos/minute |
| event_kind | Distinguir conclusão de registro parcial/sessão; quantidade não é conclusão automática |
| idempotency_key | Evitar duplicar marcação por retry/clique repetido |
| created_at / updated_at / voided_at? | Auditoria e correção/anulação sem valores negativos artificiais |

Exemplo: Escovar dentes ideal 3/dia, dois logs count=1 em 11/10 → 2/3. Em 12/10, sem registros → 0/3, sem alterar a meta e sem carregar dívida. Para garrafas, cada marcação pode registrar quantity=1; para ml, registrar o volume; para tempo, registrar minutos da sessão.

O progresso agrega logs compatíveis por Activity, metric, unidade e período, respeitando validade da meta. Um mesmo evento pode alimentar meta diária e semanal compatíveis; não duplicar o log para cada Goal. Registros destinados a uma meta específica devem ter semântica explícita para não serem contados duas vezes. A anotação goal_id não dispensa compatibilidade de unidade/métrica e não deve ser usada como filtro universal que perca registros sem goal_id.

Se uma sessão gerar conclusão e duração para metas diferentes, distinguir as medições e correlacioná-las como uma mesma execução; não somar dois eventos como duas conclusões. Recorrência após conclusão dependerá de evento de conclusão, não de qualquer incremento de quantity.

Correções precisam preservar contexto: recomendar anular a medição anterior e registrar substituta associada, ou manter auditoria de edições. Não implementar esse mecanismo agora. FKs de histórico devem impedir exclusão silenciosa de Activity/Goal/Occurrence referenciados.

O texto livre de unidade atual não diz se a quantidade é discreta ou contínua. A interface futura de quadradinhos para quantity exigirá metadado explícito, como quantity_mode ou um catálogo de unidades, em etapa própria. Não inferir automaticamente que qualquer unidade customizada aceita marcação inteira e não criar esse campo sem UX aprovada.

## 15. Occurrence futura e fronteiras

`occurrences` é adiada. Não há dependência técnica que obrigue sua criação na V0.2.3B.

Fronteiras recomendadas:

- FK (user_id, activity_id) para o mestre.
- Origem opcional recurrence_rule_id ou fixed_schedule_id, sempre da mesma Activity/dono; a variável planejada pode não ter nenhuma delas.
- Identidade própria para planejamento pontual, exceção, cancelamento ou reagendamento; unicidade futura de origem+posição nominal evita duplicar geração por retry.
- Data/horário planejado e instantes resolvidos são da ocorrência. Edição de uma ocorrência não muda automaticamente a Activity.
- Exceção referencia a identidade/posição nominal da recorrência para sobreviver a reagendamento; não usar apenas o novo start como identidade da série.
- Compromisso recorrente deriva da config e regra; fixa deriva de grupo; variável só aparece após planejamento explícito.
- Lembrete pode ter ocorrência sem bloco obrigatório; Meta / Checklist pode registrar progresso sem Occurrence e fica fora da grade principal.
- FKs de origem devem preservar histórico: não cascatar exclusão das regras/grupos sobre ocorrências. Antes dessa etapa, definir retenção de origem e snapshot do tipo/config relevante ao planejamento.

Não detalhar agora motor, resolução de timezone, exceções, disponibilidade ou algoritmo de geração. O esquema mestre já terá IDs estáveis e chaves compostas necessárias.

## 17. Mapeamento TypeScript ↔ banco

Tipos gerados do Supabase representam linhas/Insert/Update, não substituem as uniões de produto. Planejar `Database` gerado, DTOs do agregado e mappers puros; nenhum deles será implementado nesta etapa. Referência: [geração de tipos Supabase](https://supabase.com/docs/guides/api/rest/generating-types).

| Domínio | Leitura / escrita relacional |
|---|---|
| ActivityBase | activities, camelCase ↔ snake_case; user_id/revision permanecem metadados da persistência |
| Duration | Reconstituir ramo por duration_mode; rejeitar shape inesperado |
| reminder.config | reminder_configs, NULL reminder_time ↔ campo ausente |
| commitment.config | commitment_configs + planning_contexts opcional |
| fixedActivity.config | fixed_schedules ordenados + planning_contexts opcional |
| variableActivity.config | planning_contexts opcional; sem linha resulta em `{}` |
| checklistGoal.config | `{}`, sem linha própria |
| Goal | goals; unit exata; targets numeric validados; NULL ideal/ends ↔ ausência |
| RecurrenceRule | recurrence_rules, interval ↔ interval_count; ordinal -1 ↔ last; demais shapes refinados |
| TimeWindow | time_windows; NULL weekdays opcional ↔ ausência; NULL rule_id ↔ ausência |
| Weekday[] | monday..sunday ↔ ISO 1..7; reconstruir ordem canônica |
| PlanningContext.travel | Criar travel somente quando ida ou volta estiver presente; preservar zero |

Ler o agregado em resposta consistente, preferencialmente uma consulta/RPC que reúna a versão e relações, evitando ler base e filhos de revisões diferentes em vários requests. Serializar UUIDs como strings; datas civis não passam por `new Date(...).toISOString()`.

A ressalva aprovada para B.1 exige minutos inteiros. O editor foi ajustado para rejeitar frações em Duration, planejamento e Goals duration, preservando decimais em quantity. Os oito testes anteriores foram mantidos e uma regressão específica foi adicionada.

Validar os DTOs na fronteira: types gerados não garantem presença de config, valores de text/CHECK nem shape JSON retornado por RPC. Testes de ida/volta devem reproduzir os oito cenários e rejeitar dados cruzados ou inconsistentes. Não usar IDs dos mocks como cast para UUID.
