# V0.2.4B.2 — Server Actions autenticadas de Áreas

Base: [especificação V0.2.4A](V0.2.4A-gestao-areas-especificacao.md) e [dados V0.2.4B.1](V0.2.4B.1-camada-dados-areas.md). Esta entrega implementa somente integração servidor/action. Não cria rota/página de gestão, UI, RPC, migration ou operação remota; não altera schema, RLS, Auth do Supabase ou grants. O proxy recebeu somente a exceção explícita de Server Actions da futura rota de Áreas.

## Interface

`app/banco-mestre/area-actions.ts` exporta somente:

```ts
createMasterArea(input: unknown): Promise<AreaMutationResult>
renameMasterArea(input: unknown): Promise<AreaMutationResult>
setMasterAreaActive(input: unknown): Promise<AreaMutationResult>
```

`AreaMutationResult`, em area-contracts.ts, é `{ok:true, area:ManagedArea}` ou `{ok:false, kind:PersistenceErrorKind, message:string}`. Não há action de DELETE, reorder, leitura ou save genérico.

Cada action valida runtime com os parsers da B.1 antes de abrir o cliente. Inputs com user_id, ordenação, auditoria de gravação ou campos extras são rejeitados. Criação aceita somente id + nome; rename e setActive mantêm snapshot esperado, sem buscar versão nova para tentar sobrescrever. Estado ativo é booleano explícito.

Após validação, cria o cliente Supabase server por execução, chama getClaims e exige sub sem erro. Só então constrói `createAreaRepository(client, data.claims.sub)` e chama o método correspondente. Não usa user_id do navegador. A factory não é usada antes da confirmação da sessão; RLS continua impondo ownership no SQL.

## Erros e segurança

Reutiliza readFailure/PersistenceError para Validation, Unauthorized, NotFound, Conflict e Unknown, preservando também o controle de fluxo do Next via unstable_rethrow. A resposta não inclui cause, erro PostgREST/SQL, user_id, claims, headers, cookies ou tokens. No sucesso, retorna somente os cinco campos previstos de ManagedArea. updatedAt permanece string original e sortPosition é metadado interno de snapshot, sem comando/UI de ordenação.

Nenhuma action faz retry. Em erro não há revalidação. Rede pode falhar após commit; a UI futura deverá manter rascunho e conferir dados reais antes de repetir uma tentativa incerta, conforme a especificação. Essas actions ainda não foram conectadas a uma tela nem validadas no navegador remoto.

## Escopo de revalidação após sucesso

- `/banco-mestre`: nomes de áreas nos filtros e cards.
- `/banco-mestre/areas`: futura listagem de gestão.
- `/banco-mestre/nova`: opções ativas disponíveis para criação.
- `/banco-mestre/[id]`, tipo `page`: detalhe exibe o nome da área.
- `/banco-mestre/[id]/editar`, tipo `page`: edição depende de nomes e disponibilidade; preserva a área original inativa.

Os padrões de páginas dinâmicas evitam N+1 para descobrir itens associados à área. Não invalidar rotas de outros módulos ou mudar o layout global. As cinco chamadas de revalidatePath só acontecem depois que o repository confirma a gravação. Não ocorre revalidação em Validation, sessão ausente/expirada, NotFound, Conflict ou falha de persistência.

O proxy permite que POST com Next-Action não vazio na rota exata /banco-mestre/areas alcance a action, mantendo as exceções anteriores de nova/editar. GET sem sessão continua redirecionando mesmo com esse header; POST comum, PUT, subrotas e prefixos semelhantes não recebem a exceção. O header não é autenticação: a action verifica getClaims/sub novamente antes do repository, e o Next mantém as proteções de ID/Origin da Server Action. Sem configuração pública válida, o proxy continua falhando fechado. A página de gestão ainda não foi criada.

## Testes e continuidade

Unitários verificam ordem validação → cliente → claims → repository, owner da sessão, normalização, snapshot inalterado, booleano explícito, retorno projetado sem diagnósticos, cinco categorias de erro, ausência de retry e invalidação apenas após sucesso. Teste de integração com repository real e PGlite cobre criar, renomear, inativar, snapshot antigo, acesso de B a A e sessão ausente, com as seis migrations existentes. Supabase Auth é simulado nesses testes; nenhuma sessão real ou credencial é usada.

Cobertura complementar inclui owner de A/B derivado de claims.sub, rejeição de user_id do browser, falha de rede/banco sem falso sucesso e ausência de invalidação durante repository pendente. O teste proxy → action sem sessão confirma Unauthorized sem construir repository, mesmo com Next-Action forjado. A matriz de rotas confirma que a exceção não se espalha a outras páginas protegidas.

Próximo passo depende de nova instrução: integrar a tela da V0.2.4C. A validação no navegador real continua prevista para C/D. Nenhuma dessas etapas foi iniciada automaticamente.

Validação local: `npm test` 86/86; `node --test --test-concurrency=1 tests/db/*.test.mjs` 61/61; lint, `npx tsc --noEmit`, build e diff-check passaram.
