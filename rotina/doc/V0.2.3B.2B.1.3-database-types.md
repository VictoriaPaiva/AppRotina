# V0.2.3B.2B.1.3 — geração e comparação de Database Types

## Decisão final — tipos oficiais adotados

Após a comparação sem divergência E identificada, `database.types.ts` passou a conter o schema oficial gerado, com os exports Row e os nove aliases nominais preservados ao final. Essa foi a opção de menor impacto: consumidores continuam importando do mesmo arquivo, sem wrapper de Database ou tipos paralelos. O snapshot `database.types.official.ts` foi removido por não ser mais necessário. As seções seguintes preservam a comparação histórica com o contrato provisório anterior; a decisão de manter dois arquivos ali descrita foi superada por esta adoção.

O comando usado foi `npx supabase gen types typescript --linked --schema public`, executado com sucesso pelo entrypoint equivalente da CLI instalada, `node node_modules/supabase/dist/supabase.js gen types typescript --linked --schema public` (2.120.0). A saída gerada foi incorporada sem modificar seu schema; foram adicionados apenas comentário de origem e aliases de compatibilidade.

Principais diferenças adotadas: numeric como number, Relationships limitadas a public, as três flags isOneToOne emitidas pela CLI, metadata PostgrestVersion e helpers oficiais. `mapper.ts` agora omite p_expected_revision na criação, usando o default SQL null já existente; edição mantém revisão explícita. O parser de unknown, numeric strings, UUIDs, datas e integralidade permanece intacto. Nenhuma diferença exige mudança de schema; a metadata de cardinalidade não altera as constraints e não é usada pelos selects simples/RPCs atuais.

O teste de catálogo foi adaptado ao formato oficial expandido e confere Row/Insert/Update, nullability, tipos, defaults/opcionalidade, ausência de generated/identity, FKs públicas e argumentos/defaults das duas RPCs. As FKs físicas para auth.users continuam sendo conferidas separadamente. O adapter SQL testa criação omitindo efetivamente o terceiro argumento, e o teste unitário exige ausência de p_expected_revision na criação. Os testes de numeric strings continuam existentes.

Nenhum segredo apareceu no arquivo gerado, nos diffs ou no relatório. Não foram adicionados tokens, cookies, e-mails, project ref ou connection strings. Não foram alterados UI, mocks, BancoMestreProvider, Auth ou migrations; não houve db push. Esta adoção é local e não repetiu operações remotas. B.2B.2 não foi iniciada.

Verificações finais após adoção: npm test 47/47, npm run test:db 48/48, npm run lint, npx tsc --noEmit, npm run build e git diff --check passaram. O build emitiu somente o aviso preexistente de cacheComponents/partialPrefetching. Considerando esses checks e as validações remotas relatadas pela usuária, a camada de persistência está tecnicamente pronta para liberar B.2B.2; a etapa não foi iniciada.

## Origem e reprodução

- Supabase CLI instalada no projeto: 2.120.0.
- Comando de referência: `npx supabase gen types typescript --linked --schema public`.
- A primeira tentativa com npx no sandbox falhou por acesso; nenhum arquivo parcial foi criado.
- A geração bem-sucedida chamou a mesma CLI instalada por seu entrypoint: `node node_modules/supabase/dist/supabase.js gen types typescript --linked --schema public`, com permissão para a consulta remota.
- stdout validado como TypeScript antes da gravação UTF-8; stderr não foi incorporado ao arquivo nem exposto em logs. Não foram adicionados tokens, project ref, connection strings ou credenciais.
- O gerador incluiu `__InternalSupabase.PostgrestVersion: "14.18"` e somente `public` como schema. `auth` e `routine_private` não são schemas exportados no arquivo.

Para comparar os tipos atuais com uma futura geração temporária, na pasta `rotina`:

```powershell
node scripts/compare-database-types.cjs caminho/novo-snapshot.ts
```

O script usa o TypeChecker do TypeScript para resolver os aliases/generics do contrato manual e comparar nomes, campos Row/Insert/Update, tipos, nullability, opcionalidade, Relationships, argumentos e retornos de RPC. Não acessa o banco, não altera arquivos e retorna um relatório JSON. Diferenças são relatadas, sem falhar ou corrigir automaticamente os contratos. O script falha se os arquivos não forem TypeScript válido.

### 1. Numeric de goals

`minimum_target` é `number|string` no manual e `number` no oficial. `ideal_target` é `number|string|null` no manual e `number|null` no oficial. Isso produz seis diferenças: dois campos em Row, Insert e Update, sem mudança de opcionalidade/nullability.

As migrations declaram ambos como PostgreSQL numeric. O manual aceita strings na fronteira de transporte por decisão explícita. `mapper.ts` recebe unknown e chama `parseDatabaseNumber`, que valida precisão, limites e integralidade antes de converter. O tipo oficial mais estreito não substitui essa validação em runtime. Uma adoção futura deve separar a definição oficial do banco da tolerância de transporte, sem editar a saída gerada nem remover os testes de numeric string.

### 2. p_expected_revision

No manual: `p_expected_revision?: number|null`. No oficial: `p_expected_revision?: number`. `p_activity` continua obrigatório e `p_relations` opcional; ambos usam Json. A migration vigente mantém `p_expected_revision integer default null`, e `aggregateToRpc` envia null explicitamente na criação.

Portanto, substituir o tipo manual diretamente estreitaria o contrato e criaria incompatibilidade de compilação onde se envia null. Antes de adotar o oficial, será preciso decidir entre omitir esse argumento na criação (usando o default SQL já existente) ou aplicar um refinamento explícito fora do arquivo gerado. Nenhuma dessas alterações foi feita nesta etapa. Isso não indica necessidade de migration.

### 3. FKs para auth.users

O manual inclui nove relações `<tabela>_user_id_fkey` para users. A saída limitada a public não inclui essas relações para o schema auth. As FKs continuam declaradas nas migrations; sua ausência em Relationships não comprova remoção no banco. As colunas `user_id` continuam presentes e não nulas. Os testes de catálogo existentes conferem as FKs das migrations, inclusive as que apontam para auth.

### 4. isOneToOne

Nas FKs compostas de `reminder_configs`, `commitment_configs` e `planning_contexts` para activities, o manual declara true e o oficial gera false. As migrations têm PK em activity_id e UNIQUE(user_id,activity_id) nessas três tabelas, garantindo no SQL no máximo uma configuração/contexto de cada tabela por atividade. A divergência está registrada como diferença da metadata gerada; esta entrega não altera as constraints nem atribui uma causa não verificada ao comportamento da CLI.

O repository atual faz leituras simples e usa RPCs para agregados; não depende da inferência de joins embutidos. Uma adoção futura deve conferir essa inferência antes de introduzir selects relacionais. O arquivo oficial foi preservado exatamente como gerado.

### 5. Metadata e exports

O oficial acrescenta `__InternalSupabase` e os helpers `Tables`, `TablesInsert`, `TablesUpdate`, `Enums`, `CompositeTypes` e `Constants`. Ele não exporta `Row` nem os nove aliases nominais `ActivitiesRow`, `AreasRow`, etc. do manual.

`contracts.ts` depende de Row/Database; mapper depende de Json e do contrato de argumentos; repository e factories Supabase dependem de Database. Uma futura substituição deve preservar os aliases públicos em uma camada de compatibilidade, além de tratar o argumento de revisão e numeric. Não foi feita migração de imports, factories ou consumidores nesta entrega.

## Limites e decisão

O relatório contém 19 diferenças nos contratos de tabelas/RPC: seis de numeric, nove FKs fora de public, três flags de relação e um argumento nullable. Metadata e exports são relatados separadamente. Não foram encontradas tabelas, colunas ou RPCs públicas faltantes em relação ao modelo atual. Tipos não demonstram RLS, grants, comportamento de PT409 ou corpo das funções; esses pontos dependem das migrations e dos smokes já confirmados.

**Decisão desta etapa:** conservar os tipos atuais e a saída oficial lado a lado, com a comparação revisável. A adoção dos tipos oficiais fica para uma alteração explícita posterior. Nenhuma necessidade de alteração de schema foi identificada por esta comparação.

## Revisão detalhada solicitada — classificação A/B/C/D/E

Esta revisão não substituiu arquivos de tipos, não modificou consumidores e não executou consultas remotas adicionais. A evidência usada é o snapshot oficial gerado, os tipos provisórios, as migrations e a compilação em memória. Não foi identificada categoria E nesse material; isso não equivale a uma nova auditoria de todas as constraints do catálogo remoto.

### Conferência por tabela

As 102 colunas abaixo existem nos dois contratos. Em todas as tabelas, Insert tem os mesmos campos obrigatórios/opcionais; Update permite omitir todos os campos e mantém os mesmos tipos/nullability, exceto numeric de goals. Nullable em Row não significa campo ausente: a propriedade é obrigatória e pode conter null. Em Insert/Update, uma propriedade opcional pode ser omitida sem permitir null em colunas NOT NULL.

| Tabela | Colunas | Nullable em Row (iguais nos dois) | Obrigatórios em Insert (iguais nos dois) |
| --- | ---: | --- | --- |
| areas | 7 | Nenhum | user_id, name |
| activities | 15 | description, duration_minutes, min_duration_minutes, ideal_duration_minutes | user_id, name, area_id, type, default_importance |
| reminder_configs | 6 | reminder_time | activity_id, user_id, reference_date |
| commitment_configs | 7 | Nenhum | activity_id, user_id, date, start_time, end_time |
| planning_contexts | 8 | location, preparation_minutes, outbound_minutes, return_minutes | activity_id, user_id |
| fixed_schedules | 9 | Nenhum | user_id, activity_id, weekdays, start_time, end_time |
| goals | 14 | ideal_target, ends_on | user_id, activity_id, metric, unit, minimum_target, period, starts_on |
| recurrence_rules | 20 | label, anchor_date, weekdays, day_of_month, ordinal, weekday, invalid_date_policy, ends_on | user_id, activity_id, basis, pattern, interval_count, unit, starts_on |
| time_windows | 16 | recurrence_rule_id, weekdays, start_time, end_time, end_day_offset, ends_on | user_id, activity_id, kind, effect, coverage, starts_on |

UUIDs são string em ambos: id, user_id, activity_id, area_id e recurrence_rule_id quando presentes, com null somente neste último. Integers/smallint são number nos dois: revision, sort_position, minutos, interval_count, day_of_month, ordinal, weekday e end_day_offset. Arrays weekdays são number[] com nullability conforme a tabela. Os tipos não codificam faixas de integer, UUID válido ou integralidade; as validações de runtime/SQL permanecem necessárias.

created_at/updated_at são timestamptz no SQL, string não nullable em Row e opcionais em Insert/Update em ambos. Datas e horários civis também são string, não Date; suas validações não podem ser removidas. Somente minimum_target/ideal_target de goals divergem em numeric, nos três shapes.

### Defaults e campos administrados pelo banco

| Escopo | Default SQL e comportamento relevante |
| --- | --- |
| Todas as tabelas | created_at/updated_at com default now(); triggers carimbam clock_timestamp(). Ambos os tipos permitem omitir os campos na escrita. |
| areas, activities, fixed_schedules, goals, recurrence_rules, time_windows | id com gen_random_uuid(), opcional em Insert. |
| reminder_configs, commitment_configs, planning_contexts | activity_id é PK sem default e obrigatório em Insert. Não é um UUID gerado independente. |
| areas | active=true; sort_position=0. |
| activities | status='active', duration_mode='unknown', revision=1. default_importance não tem default SQL, embora a RPC forneça 'important' quando ausente no payload. |
| fixed_schedules | sort_position=0. |
| goals, recurrence_rules | enabled=true; sort_position=0. interval_count e starts_on não têm default e são obrigatórios. |
| time_windows | sort_position=0. |

Nullable sem default também permite omissão em Insert; isso é diferente de haver uma expressão DEFAULT explícita. Nenhum dos dois arquivos registra o valor literal do default, somente a opcionalidade decorrente dele. As migrations não declaram colunas GENERATED ALWAYS/identity: UUID default, timestamps e revision são defaults/triggers. Por isso, id, user_id, created_at e revision não aparecem como never no Update oficial. Isso não autoriza alterar esses campos: triggers, RLS e validação da RPC continuam prevalecendo. Esse limite de representação é compartilhado pelos dois contratos.

| Diferença | Classe | Fundamentação / ação futura |

### Compilação simulada sem gravar arquivos

O CompilerHost foi sobreposto somente em memória, usando as opções reais de tsconfig.json:

1. Oficial puro no lugar do provisório: dois erros, TS2305 por Row em contracts.ts e TS2322 por number|null em mapper.ts.
2. Oficial com Row e aliases de compatibilidade: resta somente TS2322 de revisão.
3. Aliases e omissão de p_expected_revision quando não há revisão: zero erros de TypeScript em todo o projeto, incluindo os cinco consumidores.

Nenhum desses ajustes foi aplicado ao código. A simulação comprova compatibilidade de compilação, não substitui os smokes reais se a adoção vier a ser implementada. Esta revisão alterou somente este relatório; os dois arquivos de tipos e as migrations foram preservados.
