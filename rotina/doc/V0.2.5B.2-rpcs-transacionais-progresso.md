# V0.2.5B.2 — RPCs transacionais concretas propostas

Data: 21/10/2026. **Desenho documental; nenhuma função/migration criada ou aplicada. Sem db push.** Complementa o [DDL proposto](V0.2.5B.2-desenho-tecnico-persistencia.md) e o [contrato B.1](V0.2.5B.1-contrato-progresso.md).

O SQL abaixo define assinaturas e algoritmos PL/pgSQL propostos. Não é um script pronto para executar: depende das seis tabelas, ACLs, triggers diferidos e dois helpers privados especificados neste documento. Deve ser compilado e testado em PostgreSQL local antes de virar migration autorizada. Não usa service_role nem concede DML histórico ao browser.

## 1. Segurança, isolamento e ordem de locks

Todas as funções públicas propostas: LANGUAGE plpgsql VOLATILE SECURITY DEFINER, owner `routine_progress_executor` restrito conforme DDL, `SET search_path = pg_catalog, pg_temp`, `SET row_security = on`. Referências a tabelas/funções de outros schemas sempre qualificadas. Não usar STRICT: NULL precisa produzir Validation, não retorno vazio silencioso. Sem overload/defaults que aceitem payload alternativo. `auth.uid()` é verificado antes de procurar qualquer chave/registro; RLS e filtros de owner permanecem obrigatórios.

Protocolo suportado: uma chamada mutante por transação HTTP PostgREST em READ COMMITTED. Não fazer batch de chamadas mutantes nem misturar save/record em uma transação arbitrária da aplicação: isso pode inverter locks já adquiridos. Rejeitar outro isolamento com 22023 no entrypoint; testes técnicos multi-sessão usam READ COMMITTED. Não tentar mudar isolamento dentro da função. Toda transação já confirmada é reconsultada depois de esperar pelo lock, por um novo comando SQL da função VOLATILE.

Namespaces de advisory locks transacionais, com forma de dois integers:

```sql
-- Tentativa: mesmo namespace para record e void.
perform pg_catalog.pg_advisory_xact_lock(
  250501, pg_catalog.hashtext(v_uid::text || ':' || p_attempt_id::text));
-- Contexto temporal do owner, inclusive quando ainda não há linha.
perform pg_catalog.pg_advisory_xact_lock(
  250502, pg_catalog.hashtext(v_uid::text));
```

Colisão do hash só serializa operações adicionais: igualdade é verificada pelas colunas completas, nunca pelo hash. Reservar esses namespaces e não usá-los em outros módulos. Locks são liberados no fim da transação, não manualmente entre verificação e commit.

| Caminho | Ordem |
|---|---|
| record novo | tentativa → temporal-owner → Activity FOR UPDATE → materialização de versões → captura de relógio |
| replay | tentativa → leitura do receipt/evento; não adquire contexto atual |
| void novo | tentativa → Activity FOR UPDATE → leitura do log/void |
| set timezone | temporal-owner → preferência; nunca Activity/tentativa |
| save/DML antigo | Activity e filhas; nunca temporal-owner/tentativa |

**Refinamento do desenho anterior:** void não usa FOR UPDATE no log. O lock da Activity serializa todos os voids de seus logs, sem conceder UPDATE histórico ao executor. Logs/voids são imutáveis e somente esses comandos podem inserir void. UNIQUE(owner,log) continua defesa final. É uma redução de privilégio, sem remover estruturas da B.1.

## 2. Helpers privados de integração

Somente funções do executor/triggers podem chamar estes helpers; nenhum USAGE/EXECUTE para authenticated/anon/PUBLIC:

- `routine_private.finalize_goal_versions(p_user_id uuid, p_activity_id uuid) returns void`: exige uid igual ao owner e lock do pai já adquirido; valida agregado, materializa versões/tombstones pendentes comparando estado atual à última versão, sem tocar revision. É o finalizador do desenho B.2; executa antes de capturar accepted_at. Não confere permissão por flag/GUC do cliente. Backfill tem caminho administrativo separado da instalação, sem bypass runtime uid nulo.
- `routine_private.assert_progress_integrity(p_user_id uuid, p_attempt_id uuid) returns void`: verifica ownership, vínculos recíprocos receipt↔efeito, tipo do comando, igualdade de accepted_at no record, associação completa e compatível às versões aceitas, unicidade e alvo do void. Não reavalia metas/fuso atuais de um replay. Chamado após inserções; triggers diferidos mantêm a mesma proteção no commit. Não executa SET CONSTRAINTS ALL e não confirma transação.

Esses helpers são dependências identificadas para implementação futura, não funções existentes. Violação interna de receipt/snapshot é erro de integridade técnico, não “operação já feita” nem autorização para novo UUID. Não criar receipt de sucesso se o helper falhar.

## 3. record_activity_progress

Assinatura e retorno (nomes de saída `o_` evitam colisões com colunas):

```sql
public.record_activity_progress(
  p_attempt_id uuid,
  p_activity_id uuid,
  p_expected_activity_revision integer,
  p_expected_date date,
  p_expected_temporal_revision bigint
) returns table (
  o_attempt_id uuid, o_log_id uuid, o_performed_on date,
  o_timezone text, o_voided boolean
)
```

Corpo proposto, dentro do envelope de segurança da seção 1:

```sql
declare
  v_uid uuid := auth.uid();
  v_previous public.progress_attempts%rowtype;
  v_pref public.user_temporal_preferences%rowtype;
  v_activity public.activities%rowtype;
  v_log public.activity_progress_logs%rowtype;
  v_accepted_at timestamptz;
  v_day date;
  v_goal_versions uuid[];
  v_log_id uuid;
begin
  if v_uid is null then
    raise sqlstate '42501' using message = 'Authentication required';
  end if;
  if current_setting('transaction_isolation') <> 'read committed' then
    raise sqlstate '22023' using message = 'Unsupported transaction context';
  end if;
  if p_attempt_id is null or p_activity_id is null
     or p_expected_activity_revision is null or p_expected_activity_revision < 1
     or p_expected_temporal_revision is null or p_expected_temporal_revision < 1
     or p_expected_date is null or not isfinite(p_expected_date)
     or p_expected_date not between date '0001-01-01' and date '9999-12-31' then
    raise sqlstate '22023' using message = 'Invalid progress command';
  end if;

  perform pg_catalog.pg_advisory_xact_lock(
    250501, pg_catalog.hashtext(v_uid::text || ':' || p_attempt_id::text));
  select a.* into v_previous from public.progress_attempts a
    where a.user_id = v_uid and a.attempt_id = p_attempt_id;
  if found then
    if v_previous.command_kind is distinct from 'record'
       or v_previous.activity_id is distinct from p_activity_id
       or v_previous.expected_activity_revision
          is distinct from p_expected_activity_revision
       or v_previous.expected_date is distinct from p_expected_date
       or v_previous.expected_temporal_revision
          is distinct from p_expected_temporal_revision then
      raise sqlstate 'PT409' using message = 'attempt-mismatch';
    end if;
    select l.* into strict v_log from public.activity_progress_logs l
      where l.user_id = v_uid and l.activity_id = v_previous.activity_id
        and l.id = v_previous.result_log_id;
    return query select p_attempt_id, v_log.id, v_log.performed_on,
      v_log.timezone_at_recording, exists (
        select 1 from public.activity_progress_voids x
        where x.user_id = v_uid and x.progress_log_id = v_log.id);
    return;
  end if;

  perform pg_catalog.pg_advisory_xact_lock(250502, pg_catalog.hashtext(v_uid::text));
  select p.* into v_pref from public.user_temporal_preferences p
    where p.user_id = v_uid;
  if not found then
    raise sqlstate 'PT409' using message = 'temporal-preference-required';
  end if;
  select a.* into v_activity from public.activities a
    where a.user_id = v_uid and a.id = p_activity_id for update;
  if not found then
    raise sqlstate 'PT404' using message = 'Activity unavailable';
  end if;
  if v_activity.revision <> p_expected_activity_revision then
    raise sqlstate 'PT409' using message = 'activity-changed';
  end if;
  if v_activity.status <> 'active'
     or v_activity.type not in ('checklistGoal','variableActivity') then
    raise sqlstate 'PT409' using message = 'activity-not-eligible';
  end if;
  perform routine_private.finalize_goal_versions(v_uid,p_activity_id);

  -- Captura única, depois de locks/materialização, nunca now()/CURRENT_DATE.
  v_accepted_at := pg_catalog.clock_timestamp();
  v_day := (v_accepted_at at time zone v_pref.timezone)::date;
  if v_pref.revision <> p_expected_temporal_revision
     or v_day <> p_expected_date then
    raise sqlstate 'PT409' using message = 'temporal-context-changed';
  end if;
  select array_agg(g.id order by g.id) into v_goal_versions
  from (
    select distinct on (h.source_goal_id) h.*
    from public.activity_goal_versions h
    where h.user_id = v_uid and h.activity_id = p_activity_id
    order by h.source_goal_id,h.version_no desc
  ) g
  where g.transition <> 'removed' and g.enabled
    and g.metric = 'count' and g.unit = 'execution' and g.period = 'day'
    and g.starts_on <= v_day and (g.ends_on is null or g.ends_on >= v_day);
  if coalesce(cardinality(v_goal_versions),0) = 0 then
    raise sqlstate 'PT409' using message = 'goal-not-eligible';
  end if;

  v_log_id := gen_random_uuid();
  insert into public.progress_attempts (
    user_id,attempt_id,command_kind,activity_id,expected_activity_revision,
    expected_date,expected_temporal_revision,result_log_id,accepted_at
  ) values (
    v_uid,p_attempt_id,'record',p_activity_id,p_expected_activity_revision,
    p_expected_date,p_expected_temporal_revision,v_log_id,v_accepted_at
  );
  insert into public.activity_progress_logs (
    id,user_id,activity_id,attempt_id,performed_on,timezone_at_recording,
    temporal_revision,accepted_at,metric,value,unit,event_kind,
    activity_name_at_recording,activity_type_at_recording,activity_revision
  ) values (
    v_log_id,v_uid,p_activity_id,p_attempt_id,v_day,v_pref.timezone,
    v_pref.revision,v_accepted_at,'count',1,'execution','measurement',
    v_activity.name,v_activity.type,v_activity.revision
  );
  insert into public.progress_log_goal_versions (
    user_id,activity_id,progress_log_id,goal_version_id
  ) select v_uid,p_activity_id,v_log_id,s.id
    from unnest(v_goal_versions) as s(id);
  perform routine_private.assert_progress_integrity(v_uid,p_attempt_id);
  return query select p_attempt_id,v_log_id,v_day,v_pref.timezone,false;
end;
```

O array de versões é capturado do estado protegido pelo lock do pai. Alterações em goals já precisam desse lock nos triggers existentes. A consulta depois da captura do relógio não adquire outro lock de contexto/Activity; tempo de execução posterior não muda a data aceita. FKs/checks podem ainda falhar: nesse caso toda a transação aborta, sem aceitação parcial. Se uma espera técnica posterior atravessar meia-noite mas o commit ocorrer, vale a aceitação capturada, não a hora de commit/resposta.

Replay não usa metas, preferência ou Activity atuais e não exige versão antiga ainda elegível. `o_voided` é estado observado na leitura; anulação posterior pode mudá-lo. Isso não altera identidade/data do receipt original. Não manter cached receipt como contador definitivo.

## 4. void_activity_progress

```sql
public.void_activity_progress(p_attempt_id uuid, p_progress_log_id uuid)
returns table (
  o_attempt_id uuid, o_log_id uuid, o_void_id uuid,
  o_performed_on date, o_voided boolean
)
```

Corpo proposto:

```sql
declare
  v_uid uuid := auth.uid();
  v_previous public.progress_attempts%rowtype;
  v_log public.activity_progress_logs%rowtype;
  v_void public.activity_progress_voids%rowtype;
  v_activity_id uuid;
  v_void_id uuid;
  v_at timestamptz;
begin
  if v_uid is null then
    raise sqlstate '42501' using message = 'Authentication required';
  end if;
  if current_setting('transaction_isolation') <> 'read committed' then
    raise sqlstate '22023' using message = 'Unsupported transaction context';
  end if;
  if p_attempt_id is null or p_progress_log_id is null then
    raise sqlstate '22023' using message = 'Invalid void command';
  end if;
  perform pg_catalog.pg_advisory_xact_lock(
    250501, pg_catalog.hashtext(v_uid::text || ':' || p_attempt_id::text));
  select a.* into v_previous from public.progress_attempts a
    where a.user_id = v_uid and a.attempt_id = p_attempt_id;
  if found then
    if v_previous.command_kind is distinct from 'void'
       or v_previous.target_log_id is distinct from p_progress_log_id then
      raise sqlstate 'PT409' using message = 'attempt-mismatch';
    end if;
    select l.* into strict v_log from public.activity_progress_logs l
      where l.user_id = v_uid and l.id = v_previous.result_log_id;
    return query select p_attempt_id,v_log.id,v_previous.result_void_id,
      v_log.performed_on,true;
    return;
  end if;

  select l.activity_id into v_activity_id from public.activity_progress_logs l
    where l.user_id = v_uid and l.id = p_progress_log_id;
  if not found then
    raise sqlstate 'PT404' using message = 'Measurement unavailable';
  end if;
  perform 1 from public.activities a
    where a.user_id = v_uid and a.id = v_activity_id for update;
  if not found then
    raise sqlstate 'PT404' using message = 'Measurement unavailable';
  end if;
  -- Novo comando SQL após eventual espera pelo pai.
  select l.* into strict v_log from public.activity_progress_logs l
    where l.user_id = v_uid and l.activity_id = v_activity_id
      and l.id = p_progress_log_id;
  select x.* into v_void from public.activity_progress_voids x
    where x.user_id = v_uid and x.progress_log_id = p_progress_log_id;
  if found then
    v_void_id := v_void.id;
    v_at := pg_catalog.clock_timestamp();
  else
    v_void_id := gen_random_uuid();
    v_at := pg_catalog.clock_timestamp();
    insert into public.activity_progress_voids (
      id,user_id,activity_id,progress_log_id,winning_attempt_id,voided_at
    ) values (
      v_void_id,v_uid,v_activity_id,p_progress_log_id,p_attempt_id,v_at
    );
  end if;
  insert into public.progress_attempts (
    user_id,attempt_id,command_kind,activity_id,target_log_id,
    result_log_id,result_void_id,accepted_at
  ) values (
    v_uid,p_attempt_id,'void',v_activity_id,p_progress_log_id,
    p_progress_log_id,v_void_id,v_at
  );
  perform routine_private.assert_progress_integrity(v_uid,p_attempt_id);
  return query select p_attempt_id,p_progress_log_id,v_void_id,
    v_log.performed_on,true;
end;
```

FK de winning_attempt_id é inicialmente diferida; void pode ser inserido antes do receipt, ambos no mesmo commit. Caso já anulado, nova tentativa recebe receipt próprio para o mesmo void, sem trocar winning_attempt_id/voided_at. A Activity é apenas lock/owner, não teste de status/tipo/revisão. Não exigir preferência atual nem confirmar data nova para corrigir um evento antigo. A agregação exclui o original por existência de void; não decrementa contador nem altera log/associações.

## 5. Definição/alteração segura de fuso

```sql
public.set_progress_timezone(p_timezone text, p_expected_revision bigint)
returns table (o_timezone text, o_temporal_revision bigint, o_today date)
```

Corpo proposto:

```sql
declare
  v_uid uuid := auth.uid();
  v_pref public.user_temporal_preferences%rowtype;
  v_at timestamptz;
begin
  if v_uid is null then
    raise sqlstate '42501' using message = 'Authentication required';
  end if;
  if current_setting('transaction_isolation') <> 'read committed' then
    raise sqlstate '22023' using message = 'Unsupported transaction context';
  end if;
  if p_timezone is null or p_timezone = '' or btrim(p_timezone) <> p_timezone
     or (p_expected_revision is not null and p_expected_revision < 1) then
    raise sqlstate '22023' using message = 'Invalid timezone command';
  end if;
  if not exists (
    select 1 from pg_catalog.pg_timezone_names z
    where z.name = p_timezone
      and (z.name = 'UTC' or position('/' in z.name) > 0)
      and z.name not like 'posix/%' and z.name not like 'right/%'
  ) then
    raise sqlstate '22023' using message = 'Unsupported timezone';
  end if;
  perform pg_catalog.pg_advisory_xact_lock(250502,pg_catalog.hashtext(v_uid::text));
  select p.* into v_pref from public.user_temporal_preferences p
    where p.user_id = v_uid;
  if not found then
    if p_expected_revision is not null then
      raise sqlstate 'PT409' using message = 'temporal-context-changed';
    end if;
    v_at := pg_catalog.clock_timestamp();
    insert into public.user_temporal_preferences (
      user_id,timezone,revision,confirmed_at,created_at,updated_at
    ) values (v_uid,p_timezone,1,v_at,v_at,v_at)
    returning * into v_pref;
  else
    if p_expected_revision is null or v_pref.revision <> p_expected_revision then
      raise sqlstate 'PT409' using message = 'temporal-context-changed';
    end if;
    if v_pref.timezone <> p_timezone then
      if v_pref.revision = 9223372036854775807 then
        raise sqlstate '22003' using message = 'Temporal revision limit reached';
      end if;
      update public.user_temporal_preferences p
        set timezone = p_timezone
        where p.user_id = v_uid and p.revision = p_expected_revision
        returning p.* into v_pref;
      -- BEFORE UPDATE impõe old.revision+1 e timestamps do banco.
      if not found then
        raise sqlstate 'PT409' using message = 'temporal-context-changed';
      end if;
    end if;
  end if;
  v_at := pg_catalog.clock_timestamp();
  return query select v_pref.timezone,v_pref.revision,
    (v_at at time zone v_pref.timezone)::date;
end;
```

Única confirmação permitida por chamada. `expected_revision NULL` significa criação, nunca overwrite. Duas abas inicializando: uma confirma, outra recebe conflito, mesmo se sugeriram a mesma zona; precisa reler para reconhecer o estado. Mesma zona com revisão atual é no-op; revisão antiga continua conflito, inclusive após A→B→A.

Não usar attempt_id de progresso para preferência: não há evento de contagem. Resposta perdida resolve-se por leitura autenticada da preferência/contexto; repetir CAS antigo pode retornar conflito seguro, não é prova de falha. Não reexecutar automaticamente com revisão recém-lida. Alteração de fuso confirmada não muda performed_on dos logs.

Trigger de preferência tem regra única: INSERT força revision=1 e timestamps do banco; UPDATE conserva owner/created_at, se zona mudou força old.revision+1 e novos timestamps, se não mudou impede alteração técnica arbitrária. RPC não tenta fornecer revision incrementada por outro caminho. Validar catálogo também no trigger; corpo público não é a única barreira.

## 6. Leitura de contexto e reconciliação

`get_progress_context()` é leitura autenticada VOLATILE sob mesmo lock temporal-owner e retorna `configured boolean, timezone text?, temporal_revision bigint?, today date?`. Sem preferência: configured=false e campos nulos; não cria linha. Com preferência: uma captura clock_timestamp convertida com AT TIME ZONE. Uma chamada após resposta perdida de set revela o estado atual, sem alegar qual aba foi autora da mudança.

Record/void reconciliam resposta perdida repetindo exatamente os mesmos argumentos/attempt_id. Rejeição sem commit não cria receipt. Após commit, receipt persiste sem TTL separado dos fatos. Não usar novo UUID para “tentar de novo” após resultado desconhecido. Se sessão expirou, Unauthorized; após login, retomar a mesma tentativa, sem enviar JWT manualmente.

## 7. Envelope de criação e ACLs futuras

Para cada função: criar/transferir ao papel restrito na mesma migration transacional, aplicar SECURITY DEFINER/search_path/row_security, revogar EXECUTE de PUBLIC, anon, authenticated, depois conceder EXECUTE da assinatura exata somente a authenticated. Não conceder USAGE routine_private a authenticated. Helpers permanecem inacessíveis. Papel executor não é membro/owner privilegiado que contorne RLS.

Nenhum INSERT/UPDATE/DELETE histórico ao browser. Executor: SELECT e INSERT necessários no histórico; sem UPDATE/DELETE e sem ownership de tabelas. Preferência tem UPDATE limitado. Activity permite lock com SELECT/UPDATE de coluna restrita conforme desenho, policy owner e proteção de identidade; não há grant UPDATE no log nem novo grant amplo em goals. Verificar RLS aplicada ao executor com sessões A/B, não apenas ao caller authenticated.

## 8. Erros, duas abas e retries técnicos

| SQLSTATE/razão | Contrato |
|---|---|
| 42501 | Sessão ausente; não escrever nem revelar existência de alvos. Erro ACL inesperado também deve ser diagnosticado internamente, sem mensagem SQL na UI. |
| PT404 | Alvo ausente/invisível, mesma mensagem segura. |
| PT409 / attempt-mismatch | UUID já aceito para outro conteúdo/espécie. Não reusar nem alterar receipt. |
| PT409 / activity-changed | Cadastro mudou; nova intenção só após atualização explícita. |
| PT409 / temporal-context-changed | Dia/revisão temporal venceu; sem migração automática da tentativa para outro dia. |
| PT409 / temporal-preference-required | Configurar fuso explicitamente antes da marcação; sem default. |
| PT409 / activity-not-eligible ou goal-not-eligible | Cadastro não aceita esta marcação no contexto atual; reler sem repetir automaticamente. |
| 22023 | Payload/contexto transacional inválido. |
| 40001 / 40P01 | Serialization failure/deadlock reais. Propagar sem converter para PT409 nem capturar como sucesso. |
| 55P03 / 57014 / falha de transporte | Lock timeout/cancelamento/resultado desconhecido: erro técnico seguro; reconciliação usa identidade original. |
| 235xx / P0002 internos inesperados | Invariante/implementação: rollback e diagnóstico privado, sem tratá-los como replay/confirmação. |

Não adicionar EXCEPTION WHEN OTHERS que esconda erro ou retorne sucesso. Sem loops de retry SQL nas RPCs. Proposta inicial: nenhum retry automático adicional na aplicação; oferecer retry/reconciliação explícito com mesma chave. Eventuais retries de infraestrutura devem ser seguros pela idempotência, mas precisam ser medidos, não presumidos inexistentes.

O mapper atual converte PT409 **e** 40001/40P01 para PersistenceError('Conflict'); PT404 ainda vira Unknown. Na implementação futura, preservar a política compartilhada ou adicionar um adaptador de progresso que distinga códigos/razões por whitelist segura antes da mensagem pública. Não afirmar hoje que já existe UX de conflito temporal ou NotFound por PT404. Diagnóstico técnico fica privado; payload de erro completo nunca vai para a UI. Este documento não altera errors.ts.

Duas abas com UUIDs diferentes e mesma revisão: dois logs; cada uma passa por seu lock de tentativa, depois contexto/Activity, sem incrementar revision por +1. Se a segunda cruza meia-noite antes da aceitação, recebe conflito de contexto. Duas anulações diferentes para o mesmo log: lock do pai serializa, segunda relê void confirmado e recebe o mesmo void_id com receipt próprio. A mesma chave usada em record e void dá attempt-mismatch.

## 9. Testes e estado

Antes de migration, compilar corpos com helpers/triggers em PostgreSQL descartável e testar READ COMMITTED com sessões concorrentes: record/record mesma chave, chaves distintas, record/save, record/set, void/void e record/void mesma chave. Forçar rollback após insert de receipt/log/associação/void e falha de constraint no commit. Simular commit com resposta perdida, retry no dia seguinte, timezone alterado e Activity removida da elegibilidade; só sessão/owner/conteúdo condicionam replay aceito.

Testar RLS/ACL com uid ausente/A/B, chamadas diretas às tabelas/helpers, nulos, conteúdo divergente, timestamp/fuso de ambiente diferentes e revisão máxima. Testar também bloqueio além da meia-noite com captura posterior à espera, sem alterar código de produção para simular relógio. Testes determinísticos de borda temporal precisam de seam privado somente no ambiente de teste, jamais parâmetro de horário exposto na RPC.
