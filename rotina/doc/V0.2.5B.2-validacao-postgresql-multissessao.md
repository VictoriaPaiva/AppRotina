## 2. Como a concorrência foi comprovada

Cada disputa usa conexões pg independentes, com pg_backend_pid distintos. A sessão vencedora mantém transação aberta depois de executar o comando. A segunda envia a operação enquanto a primeira ainda não confirmou. Uma conexão observadora consulta pg_blocking_pids e exige evidência de bloqueio pelo backend esperado antes de liberar COMMIT.

Assim, os testes não confundem Promise.all com concorrência efetiva nem dependem de um sleep arbitrário para supor sobreposição. Espera de observação tem deadline; statement_timeout/lock_timeout limitam falhas e o runner impõe timeout de teste. Dados/receipts são lidos após as transações para verificar o efeito confirmado.

## 3. Matriz de resultados

| Caso | Resultado observado |
|---|---|
| 1. Mesmo attempt_id/conteúdo sobrepostos | Segunda sessão esperou pela chave; um único log e receipt com mesma identidade/data. |
| 2. Mesma chave/conteúdo diferente | Primeiro confirmou; segundo retornou PT409/attempt-mismatch; um log. |
| 3. Duas tentativas distintas | Duas execuções válidas; IDs diferentes; revision da Activity não mudou pelo progresso. |
| 4a. Mudança de fuso vence record | Record aguardou lock temporal e rejeitou expectedTemporalRevision vencida, sem log. |
| 4b. Record vence mudança de fuso | Fuso aguardou; replay depois da alteração conservou dia/fuso/ID originais. |
| 5a. Record vence save que muda nome/alvo | Save aguardou Activity; log continuou associado ao ideal 3, nova versão guardou ideal 5. |
| 5b. Save desativa Goal antes do record | Record aguardou e retornou activity-changed por expectedActivityRevision antiga, sem gravação. |
| 6. Dois voids com tentativas distintas | Uma anulação efetiva; mesmo void_id; receipts próprios de cada tentativa. |
| 7a. Save remove Goal antes do record | Tombstone confirmado; record antigo rejeitado, sem medição. |
| 7b. Record antes da remoção | Log, associação e versão original preservados; tombstone posterior confirmado. |
| 8. Fila com record, outro record, timezone e save | Operações terminaram com sucesso ou conflito funcional esperado; nenhum deadlock/40001 nesses fluxos suportados. |
| 9a. Inversão de locks provocada deliberadamente | Deadlock real do servidor produziu 40P01 em uma das RPCs; não PT409. |
| 9b. Snapshot conflitante real | UPDATE em REPEATABLE READ produziu 40001 nativo; não PT409. |
| 10. Commit confirmado, resultado descartado e conexão fechada | Nova conexão repetiu a mesma tentativa e recuperou o log original; total continuou 1. |

São 14 testes porque fuso, save e remoção foram exercitados nas duas ordens, e erros técnicos têm dois casos distintos. Nenhum foi marcado como skip.

### Limites explícitos dos testes negativos

No 9a, a sessão cria uma inversão não suportada: bloqueia Activity manualmente e só depois chama set_progress_timezone, enquanto record detém temporal-owner e espera Activity. Isso demonstra propagação de deadlock real e a importância do contrato de ordem de locks; não revela deadlock previsível nos entrypoints usados como uma chamada por transação. A vítima pode ser qualquer backend, e o teste verifica ambos os resultados sem depender da ordem de chegada das mensagens.

No 9b, 40001 foi provocado por duas transações SQL reais em REPEATABLE READ, sem RAISE EXCEPTION injetado. O entrypoint de progresso exige READ COMMITTED e rejeita isolamento diferente com Validation; portanto este teste não afirma ter produzido 40001 dentro de record. Além do erro nativo, verifica-se que a candidata não tem handler que converta serialization_failure/deadlock em PT409. O mapper compartilhado da aplicação ainda agrupa códigos técnicos em Conflict; ele não foi alterado nesta entrega.

No 10, a perda é simulada no consumidor: o teste descarta o resultado confirmado e fecha a conexão antes de reconciliar em outra sessão. Não é injeção de perda de pacote TCP durante COMMIT, nem teste de failover do serviço. Prova a reconciliação depois de um commit cujo resultado deixou de estar disponível ao chamador.

## 4. Ajustes necessários

**Nenhum ajuste novo no SQL da candidata foi necessário para os cenários concorrentes suportados.** Ela mantém as correções de ownership/backfill do preflight B.2.1. Corpo/assinatura/SECURITY INVOKER/PT409/revision de save permanecem intactos.

Ajustes ficaram no harness:

- Windows: esperar o evento exit do pg_ctl, sem aguardar fechamento de pipes que o postmaster pode herdar; isso evita travar o runner com servidor já pronto.
- Usar o banco padrão de um cluster novo verificado, evitando clonagem de database e seu custo de I/O no setup.
- No ambiente Codex, iniciar o cluster fora do token restrito que impede pg_ctl de criar seu processo. O listener continua somente local; não se alterou arquitetura ou configuração do produto por isso.
- Inspeção de blockers antes de COMMIT e aceitação das duas ordens possíveis de entrega do erro de deadlock.

O cluster bem-sucedido foi parado no finally do runner. Logs/dados técnicos permanecem somente no cache ignorado para diagnóstico. Nenhuma migration antiga ou pasta migrations foi alterada.

## 5. Reproduzir

A partir de rotina:

```powershell
npm.cmd ci
# Extrair os binários PostgreSQL 17 da fonte oficial em um diretório local.
# Caminho padrão: node_modules/.cache/rotina-pg17/pgsql/bin
# Ou informar um diretório existente (sem connection string):
$env:ROTINA_PG_BIN = 'C:\caminho\postgresql17\bin'
npm.cmd run test:pg:local
```

O runner não baixa/executa binários automaticamente. Exige postgres/initdb/pg_ctl e versão major 17; não tenta fallback para o remoto. Os caminhos de binários podem ser externos, mas clusters são sempre criados no cache local do projeto. `npm ci` pode limpar node_modules e seu cache, então provisionar os binários depois desse comando ou usar ROTINA_PG_BIN fora de node_modules.

Não executar o arquivo de testes diretamente apontando porta de banco existente. Ele exige também o diretório do cluster gerado pelo runner e verifica correspondência antes de alterar schema. Não instalar a candidata no projeto principal para reproduzir.

A lacuna de concorrência e de major 17 **local** foi exercitada nos cenários definidos; não é prova universal de ausência de deadlocks ou validação de carga prolongada. Não foram testados failover, perda TCP durante COMMIT, meia-noite/DST por relógio controlado, nem customizações/grants efetivos do Supabase gerenciado.

**Candidata ainda não pronta para db push.** Continuam necessários: preflight do projeto Supabase com papel efetivo de migrations, auditoria restante de integridade/ACL, política de eliminação de conta/retention, bordas temporais e avaliação de instalação/backfill sob carga.
