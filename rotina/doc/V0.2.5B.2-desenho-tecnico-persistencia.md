# V0.2.5B.2 — desenho técnico proposto da persistência

Data: 21/10/2026. **Status: desenho documental iniciado; SQL abaixo é proposta, não migration executável completa nem schema aplicado.** Não foram criados arquivos em migrations, funções no banco ou código funcional. Sem db push.

Base: contratos [temporal](V0.2.5B.1-contrato-temporal-progresso.md), [histórico](V0.2.5B.1-contrato-historico-progresso.md) e [consolidado B.1](V0.2.5B.1-contrato-progresso.md). Inspecionadas as seis migrations atuais, em especial integridade, hardening privado e a substituição vigente de save em `20261019000100_revision_conflict_http_409.sql`. O conflito customizado vigente é PT409, não o 40001 do corpo histórico anterior.

## 1. Limites e decisões técnicas

Manter as seis estruturas de B.1. Dados de comando serão colunas tipadas, sem JSON arbitrário de receipt ou hash usado como única prova de igualdade. Logs e versões conservam fatos; voids expressam correção; associações não multiplicam o valor.

Schema `public` permite tipos oficiais futuros; helpers continuam em `routine_private`, sem USAGE/EXECUTE concedidos ao cliente. Funções públicas novas serão SECURITY DEFINER sob papel dedicado restrito, **sem alterar SECURITY INVOKER de save**. Proposta deve passar por validação local de DDL, triggers, ACLs e concorrência antes de se tornar migration.

## 2. DDL das seis tabelas

Os comandos estão ordenados para resolver referências circulares com ALTER TABLE ao final. Todos os ON DELETE são RESTRICT, inclusive auth.users: a proposta bloqueia eliminação administrativa da conta até existir fluxo explícito de expurgo, em vez de herdar cascata destrutiva. ON UPDATE é RESTRICT; IDs/owner são imutáveis. Não adicionar defaults `auth.uid()` que permitam escrita pública indireta: o comando confiável preenche owner.

### 2.1 Preferência temporal

```sql
create table public.user_temporal_preferences (
  user_id uuid primary key references auth.users(id)
    on update restrict on delete restrict,
  timezone text not null check (btrim(timezone) = timezone and timezone <> ''),
  revision bigint not null default 1 check (revision >= 1),
  confirmed_at timestamptz not null default clock_timestamp()
    check (isfinite(confirmed_at)),
  created_at timestamptz not null default clock_timestamp()
    check (isfinite(created_at)),
  updated_at timestamptz not null default clock_timestamp()
    check (isfinite(updated_at))
);
```

PK basta para lookup/lock. Não existe default de timezone. Trigger BEFORE INSERT/UPDATE valida nome exato em pg_catalog.pg_timezone_names: aceitar UTC ou nome com `/`, excluir prefixos posix/ e right/ e nomes abreviados sem região. Isso é uma política de aceitação de identificadores do catálogo, não normalização automática de aliases; o nome confirmado é preservado. Impede alteração de owner/created_at e impõe revision=old+1 em mudança real de zona, relógio do banco para confirmação/auditoria. Overflow rejeita. Mesma zona com revisão esperada correta é no-op; A→B→A incrementa duas vezes. Não usar CHECK que consulta catálogo: validação dinâmica pertence ao trigger. Não usar `valid_date` privado em CHECK novo, evitando nova exceção EXECUTE para cliente.

### 2.2 Tentativas e receipts tipados

```sql
create table public.progress_attempts (
  user_id uuid not null references auth.users(id)
    on update restrict on delete restrict,
  attempt_id uuid not null,
  command_kind text not null check (command_kind in ('record','void')),
  activity_id uuid not null,
  target_log_id uuid,
  expected_activity_revision integer,
  expected_date date,
  expected_temporal_revision bigint,
  result_log_id uuid not null,
  result_void_id uuid,
  accepted_at timestamptz not null check (isfinite(accepted_at)),
  created_at timestamptz not null default clock_timestamp()
    check (isfinite(created_at)),
  primary key (user_id, attempt_id),
  unique (user_id, activity_id, attempt_id),
  foreign key (user_id, activity_id)
    references public.activities(user_id,id) on update restrict on delete restrict,
  check (
    (command_kind = 'record' and target_log_id is null
      and expected_activity_revision is not null and expected_activity_revision >= 1
      and expected_date is not null and isfinite(expected_date)
      and expected_date between date '0001-01-01' and date '9999-12-31'
      and expected_temporal_revision is not null and expected_temporal_revision >= 1
      and result_void_id is null)
    or
    (command_kind = 'void' and target_log_id is not null
      and target_log_id = result_log_id and result_void_id is not null
      and expected_activity_revision is null and expected_date is null
      and expected_temporal_revision is null)
  )
);
create index progress_attempts_activity_idx
  on public.progress_attempts(user_id,activity_id);
```

Não há estado pending confirmado, TTL, receipt alterável ou UNIQUE global da tentativa. `accepted_at` é instante de aceitação deste comando; receipt do void pode apontar para anulação efetivada antes por outra tentativa. Replay compara espécie/alvo/todas as pré-condições armazenadas, sem comparar instante gerado. record sempre representa count/1/execution; esse conteúdo não vem do input.

Sem FK à preferência atual: mudar a zona/revision não invalida snapshots antigos. Owner deriva da FK à Activity; não precisa repetir FK direta auth.users. Sem goal_id, updated_at, occurred_at inventado ou coluna voided editável. Regra civil=conversão(accepted_at,zona), snapshot/revision e elegibilidade são verificações de inserção no mecanismo confiável, não CHECK que voltaria a converter histórico com uma tzdata atualizada.

### 2.4 Versões de metas

```sql
create table public.activity_goal_versions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null,
  activity_id uuid not null,
  source_goal_id uuid not null,
  version_no bigint not null check (version_no >= 1),
  activity_revision integer not null check (activity_revision >= 1),
  transition text not null check (transition in ('baseline','upsert','removed')),
  effective_at timestamptz not null check (isfinite(effective_at)),
  created_at timestamptz not null default clock_timestamp()
    check (isfinite(created_at)),
  enabled boolean not null,
  metric text not null check (metric in ('count','duration','quantity')),
  unit text not null check (btrim(unit) <> ''),
  minimum_target numeric not null
    check (minimum_target > 0 and minimum_target <= 9007199254740991),
  ideal_target numeric check (ideal_target >= minimum_target
    and ideal_target <= 9007199254740991),
  period text not null check (period in ('day','week','month')),
  starts_on date not null check (isfinite(starts_on)
    and starts_on between date '0001-01-01' and date '9999-12-31'),
  ends_on date check (ends_on is null or (isfinite(ends_on)
    and ends_on between date '0001-01-01' and date '9999-12-31')),
  check (ends_on is null or ends_on >= starts_on),
  check (
    (metric = 'count' and unit = 'execution'
      and minimum_target = trunc(minimum_target)
      and (ideal_target is null or ideal_target = trunc(ideal_target)))
    or (metric = 'duration' and unit = 'minute'
      and minimum_target = trunc(minimum_target) and minimum_target <= 2147483647
      and (ideal_target is null or
        (ideal_target = trunc(ideal_target) and ideal_target <= 2147483647)))
    or metric = 'quantity'
  ),
  unique (user_id,activity_id,id),
  unique (user_id,source_goal_id,version_no),
  foreign key (user_id,activity_id)
    references public.activities(user_id,id) on update restrict on delete restrict
);
create index activity_goal_versions_latest_idx
  on public.activity_goal_versions(user_id,activity_id,source_goal_id,version_no desc);
```

Constraints de métrica espelham goals atual, incluindo limites numéricos. `removed` guarda último snapshot completo; `transition` governa elegibilidade, mesmo se enabled antigo for true. Sem FK source_goal_id→goals: remoção viva é permitida. Trigger verifica que origem não migra de Activity na mesma conta, sequência começa em 1 e segue +1 sob lock do pai; tombstone é terminal para o UUID removido. Uma versão reativada após enabled=false usa upsert, mas não após removed. Instantes iguais são ordenados por version_no, não por relógio local. Sem unique por activity_revision: múltiplas origens podem compartilhar revisão.


MATCH SIMPLE permite FK de void nula em record, mas CHECK de command_kind torna todos os componentes obrigatórios em void. Trigger diferido confere: log referencia tentativa record cujo result_log_id é o próprio log e instante coincide; void aponta para tentativa void cujo alvo/resultados são esse log/void. Receipts adicionais de void apontam para o mesmo fato, sem precisarem ser vencedores. Nenhum receipt órfão ou efeito sem receipt pode confirmar.

## 3. Constraints que exigem trigger, não CHECK entre tabelas

Lista obrigatória de implementação, não nomes de helpers já existentes:

1. Validação IANA/preferência e proteção de owner/revision/timestamps.
2. Imutabilidade: BEFORE UPDATE OR DELETE que rejeita em attempts/logs/versions/associações/voids, mesmo para o papel executor. Preferências permitem somente UPDATE controlado. Sem TRUNCATE concedido.
3. Integridade receipt↔efeito e existência de associações: CONSTRAINT TRIGGER AFTER INSERT, DEFERRABLE INITIALLY DEFERRED. Validar antes de responder na RPC com verificação explícita do alvo; o commit também protege caminhos internos. Não executar SET CONSTRAINTS ALL indiscriminadamente, pois afeta validação do agregado alheia ao comando.
4. Sequência/origem/transições de versões e compatibilidade das associações: validar sob lock da Activity na inserção. Verificação diferida não deve recalcular elegibilidade com cadastro que mudou depois da aceitação na mesma transação; usar versões e ordem capturadas.

Cada helper de trigger tem search_path `pg_catalog, pg_temp`, referências qualificadas e não aceita SQL/identificadores do cliente. Triggers de integridade não expõem API EXECUTE. Sem bypass baseado em custom GUC/flag manipulável. Esses corpos ainda precisam ser escritos/testados na fase autorizada de implementação; os CREATE TABLE isolados não satisfazem o contrato.

## 4. Ownership SQL, RLS e grants

Separar owner das tabelas (papel de migration) de `routine_progress_executor`: NOLOGIN, NOSUPERUSER, NOBYPASSRLS, NOINHERIT; não membro de authenticated/service_role nem concedido a authenticator/anon/authenticated. Não dar ownership de tabelas nem CREATE de schema ao executor em runtime. Migration controla criação/transferência das funções e revoga permissões temporárias de deployment no mesmo commit.

Executor: USAGE em public/routine_private/auth, EXECUTE em auth.uid(), SELECT nas seis tabelas e activities/goals, INSERT nas cinco tabelas históricas, INSERT/UPDATE na preferência. Nenhum UPDATE/DELETE em histórico. Em activities, SELECT FOR UPDATE necessita privilégio UPDATE; conceder somente UPDATE(id) ao executor para essa finalidade, sem API que altere id. RLS owner_update específica aplica-se ao papel, com USING/WITH CHECK auth.uid()=user_id; trigger de identidade mantém id imutável. Reavaliar grants exatos com teste negativo de DML e lock, sem conceder UPDATE amplo por conveniência.

Aplicar este template **a cada uma das seis tabelas**, na migration futura (não executado):

```sql
-- repetir substituindo <table> por cada tabela acima
alter table public.<table> enable row level security;
alter table public.<table> force row level security;
revoke all on public.<table> from public, anon, authenticated;
grant select on public.<table> to authenticated, routine_progress_executor;
create policy owner_read on public.<table> for select
  to authenticated, routine_progress_executor
  using (user_id = (select auth.uid()));
create policy executor_insert on public.<table> for insert
  to routine_progress_executor
  with check (user_id = (select auth.uid()));
grant insert on public.<table> to routine_progress_executor;
```

Somente em user_temporal_preferences: UPDATE(timezone,revision,confirmed_at,updated_at) ao executor, policy UPDATE com USING e WITH CHECK owner. Demais tabelas: sem policy UPDATE/DELETE e trigger imutável. anon não tem SELECT/EXECUTE. authenticated não tem DML nem REFERENCES/TRIGGER/TRUNCATE. Não alterar policies/grants das tabelas antigas globalmente; adicionar políticas de leitura/lock ao executor em activities/goals sem abrir acesso cruzado. Backfill administrativo é operação de migration auditada, com auth.uid ausente tratada explicitamente no caminho de instalação, sem criar exceção runtime para sessão nula.

Revogar EXECUTE de PUBLIC/anon/authenticated em cada função nova imediatamente na mesma transação de criação; depois conceder somente as RPCs públicas listadas abaixo a authenticated. Ajustar default privileges do papel criador sem reabrir routine_private. Não presumir que os defaults endurecidos em migrations antigas abrangem owners novos.

## 5. RPCs propostas e protocolo

| Nome/argumentos propostos | Retorno seguro | Comportamento |
|---|---|---|
| get_progress_context() | date, timezone, temporal_revision ou estado preference-required | Captura relógio do banco e contexto próprio; não inventa preferência. |
| set_progress_timezone(p_timezone text, p_expected_revision bigint) | timezone, revision, date | Inicialização usa expected_revision NULL somente se não existir; update exige revisão atual. Lock transacional por owner cobre linha ainda ausente. |
| record_activity_progress(p_attempt_id uuid, p_activity_id uuid, p_expected_activity_revision integer, p_expected_date date, p_expected_temporal_revision bigint) | attempt_id, log_id, performed_on, timezone, voided | Cria/replay de +1; nenhum parâmetro com default, todos NN. |
| void_activity_progress(p_attempt_id uuid, p_progress_log_id uuid) | attempt_id, log_id, void_id, performed_on, voided=true | Corrige/replay mesmo após inativar/remover meta; não recebe nova data. |

Retornos TABLE tipados, não registro completo de attempts/logs. Todas exigem auth.uid NN e sessão normal, SECURITY DEFINER com owner restrito/search_path fixo e objetos qualificados. VOLATILE para comandos/contexto com relógio atual; não usar STRICT para deixar argumento nulo virar sucesso vazio: validar explicitamente e retornar Validation. preferências usam CAS; não precisa de progress_attempts porque não é medição: resposta perdida resolve-se relendo preferência, sem novo UPDATE automático.

Locks de tentativa: `pg_advisory_xact_lock` com hash estável de namespace+owner+attempt (colisão só serializa desnecessariamente, nunca define igualdade). Depois reconsultar receipt. Lock temporal por owner separado, usado por set/contexto de record; depois lock da Activity. Void: tentativa→Activity→log. Save/direct DML: Activity, nunca adquire lock temporal/tentativa. Todos os caminhos obedecem à ordem; nenhuma espera de lock relevante após capturar accepted_at. Captura e ordenação final serão verificadas com sessões concorrentes reais, pois PGlite não substitui esse teste.

Record: autenticar/validar→serializar tentativa→replay/comparar payload→lock temporal e Activity→materializar versões vigentes→validar revision/elegibilidade→capturar relógio→validar dia/revisão temporal→inserir tentativa+log+associações→validar integridade→retornar. Materializar versão não altera Activity revision. Void: verificar alvo próprio, serializar com outros voids, inserir um fato/receipt; se já anulada, novo receipt reutiliza void existente. Retry recupera receipt antes de checar cadastro/contexto novos.

Erros: 42501 para sessão ausente, PT404 para alvo não visível, PT409 com razões públicas limitadas (`attempt-mismatch`, `activity-changed`, `temporal-context-changed`), 22023 para input inválido. Mapper futuro deve mapear esses códigos com mensagens seguras; não devolver detalhes de constraints. 40001/40P01 reais permanecem distintos. Política de retry técnico exige mesma identidade/conteúdo, nunca novo UUID.

## 6. Captura de Goal e save atual: solução proposta

O hardening atual revoga EXECUTE privado do authenticated. Portanto save invoker **não poderá chamar diretamente helper privado novo**. Não reabrir schema nem helpers para resolver isso.

Usar constraint triggers diferidos de captura em goals/activities, com owner executor restrito, e um finalizador privado idempotente por Activity. Ele compara o conjunto atual com a última versão por origem, gera baseline/upsert/tombstone apenas para diferenças semânticas e lê revision final do pai bloqueado. Triggers atuais já bloqueiam/tocam o pai; manter a integridade diferida existente. Finalizador não altera Activity e não dispara recursão de touch_parent.

Save preserva assinatura/invoker/PT409 e a sequência de validação atual; sua futura substituição deve garantir que o resultado só seja tratado como confirmado depois da captura e commit. Capture triggers realizam a proteção sem chamada EXECUTE privada do invoker. A RPC de progresso definer pode chamar o mesmo finalizador antes da marcação, para transação que alterou o cadastro e ainda não disparou triggers diferidos. Eventos preservam versão realmente usada; outra edição posterior na mesma transação gera versão posterior, sem reatribuir o log.

O finalizador também cobre DML direto de goals: nenhuma dependência de flag indicando “veio do save”. Para uma transação com várias mudanças sem medição intermediária, diferir captura evita versões de estados transitórios. Remoção e reinserção da mesma origem já tombstonada em commit anterior são rejeitadas; tentativa de migrar UUID de origem para outra Activity é rejeitada. Locks por origem se necessários devem ser definidos sem inverter lock do pai; não aceitar SELECT desprotegido para impedir reuso entre pais concorrentes.

Unicidade de origem entre pais: consultar a última versão por (owner,source_goal_id), não apenas por Activity; rejeitar se outro pai já detém a origem. Duas origens novas concorrentes tentam ambas version_no=1; UNIQUE(owner,source_goal_id,version_no) impede dupla aceitação, sem estrutura extra. Não fazer ON CONFLICT que ignore esse erro: reverter com conflito seguro. A tentativa perdedora não pode incrementar sequência e anexar outra Activity. Para origem existente, verificar pai em todo INSERT de versão. Índice único existente cobre lookup e corrida inicial; tombstone mantém reserva permanente do UUID.

Nomear o constraint trigger de captura depois de aggregate_valid na ordem de disparo e executar também a validação do agregado antes de gerar versões. Se o chamador antecipar constraints, estado inválido falha atomicamente; estados válidos efetivamente capturados podem produzir versões intermediárias na mesma transação, preservadas se houve medição entre eles. Não usar a antecipação como bypass. Testar esse comportamento e rollback antes de promover a proposta a migration; o caso comum diferido continua capturando apenas o estado final quando não há marcação intermediária.

## 7. Instalação, backfill e testes exigidos

Migration incremental futura em uma transação: preflight de role/ownership/versão PostgreSQL→locks de escrita nas tabelas mestre relevantes→tabelas e índices→policies/grants/helpers/triggers→captura baseline das metas existentes→RPCs/grants finais→verificação ACL/constraints. Nenhum log artificial; nenhuma preferência inferida. Índices não usam CONCURRENTLY dentro dessa transação. Backfill registra coverage a partir da instalação, não antiguidade inventada.

Revisão de eliminação de conta é gate: FK RESTRICT bloqueia cascatas existentes por auth.users; documentar resposta operacional em vez de permitir perda histórica. Sem DELETE funcional ou expurgo implícito.

Antes de criar/aplicar migration: compilar SQL completo em banco local descartável com seis migrations, testar FKs circulares/constraints diferidas, NaN/Infinity/nulos, snapshot forjado, ACL por papel, FORCE RLS, trigger imutável, IANA ausente/inválido, snapshots após tzdata e todos os casos B.1. Verificar replay após meia-noite/commit perdido, dois UUIDs, duplo void e alteração Goal/save/DML direto. Concorrência/locks precisam também de PostgreSQL multi-sessão; PGlite sozinho não basta. Suites existentes não foram executadas para esta documentação.
